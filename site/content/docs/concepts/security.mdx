boxer's threat model is **a careless agent, not a hostile one**. Read this page before relying on
boxer for anything else.

## What the boundary is

A sandbox sees only what boxer mounts into it:

- the git worktree, read-write;
- the host's package caches for the lockfiles the worktree has (`~/.npm` for `package-lock.json`,
  and so on), read-only, unless `[cache] enabled = false`;
- anything you list in `mounts`.

A command in the guest cannot read your home directory, your SSH keys, your cloud credentials or
any other host path. On the default backend, smolvm, the network is an allowlist: the registry
hosts the image needs, plus whatever you name in `allow_hosts`, and nothing else.

How strong the boundary is depends on the [backend](/docs/concepts/backends). `boxer doctor`
prints which one you have:

| backend | boundary | egress |
| --- | --- | --- |
| `smolvm` (default) | a kernel per sandbox | allowlist by default |
| Apple `container` | a kernel per sandbox | on or off, no allowlist |
| `docker`, `podman` | **one kernel shared by every sandbox on the machine** | on or off, no allowlist |

A backend that cannot enforce the allowlist **refuses** `network.mode = "allowlist"` rather than
run with a network boxer said it would deny. A container escape on a shared-kernel backend reaches
every sandbox on that machine; on a kernel-per-sandbox backend it reaches one guest. If
containment is why you use boxer, keep the default.

Within that boundary, a dependency's postinstall script runs where there is nothing worth taking,
and a command that reconfigures the machine reconfigures a sandbox you can delete with
`boxer down`.

<Callout type="warn">
The worktree is your real worktree, mounted read-write. `rm -rf` inside it deletes your files from
the guest exactly as from the host. The boundary protects everything else on your machine, not the
code the agent is working on.
</Callout>

## What it is not

boxer is not a defence against an agent that can choose to run something on the host. These paths
stay on the host by design, and each is a hole if your threat model is adversarial:

**`passthrough` programs.** `git`, `gh`, `ssh`, `boxer` and `smolvm` run unsandboxed by default,
because they need your credentials and your real repository. `gh` alone reaches anything your
GitHub token reaches.

**`mode = "off"` and `enforcement = "audit"`.** Neither sandboxes anything. `audit` prints what boxer
would have rewritten or blocked, and runs the command on the host.

**Commands `intercept` does not name.** In `rewrite` mode boxer rewrites the commands it
recognises; anything else runs on the host. PATH shims and `tool` mode narrow this gap, which is
why `enforcement = "both"` is the default, but they do not close it. See
[Enforcement](/docs/guides/enforcement).

**`on_sandbox_unavailable = "passthrough"`.** Off by default (`"fail"`). When set, a command whose
sandbox cannot be provisioned runs on the host instead of failing.

## If the threat model is adversarial

Run the harness inside the guest:

```toml
integration = "inside"
```

```sh
boxer shell claude
```

The agent is not on the host, so there is no host shell to reach and nothing to intercept. The
cost: every harness config directory that exists on the host (`~/.claude`, `~/.codex`, ...) is
mounted read-write into the guest, so the harness's credentials are inside the sandbox. See
[Running the harness inside](/docs/guides/inside).

## Repository configuration is executable input

A `boxer.toml`, a skill or a plugin in a repository is code you are about to run. `setup`,
`image_setup`, `start` and `[tasks]` execute in the guest. `[prep]` commands, and hooks and MCP
servers named in a harness's configuration, execute **on the host**.

Treat a repository's boxer configuration like its `Makefile` or its `package.json` install
scripts. boxer never fetches configuration or content from the network, so what runs is what is
in the checkout.

## Forwarded ports and URLs

A port in `network.ports` is a way in from the host to the guest. boxer binds it to `127.0.0.1`
on every backend, so only processes on this machine can reach it, not the local network. docker,
podman and Apple `container` publish on every interface by default; boxer passes the loopback
address explicitly. To expose a port on purpose, name the address in the spec:
`"0.0.0.0:3000:3000"`.

The portless proxy behind [`[urls]`](/docs/guides/urls) also listens on loopback only (`127.0.0.1`
and `::1`), unless someone started it with `portless proxy start --lan`. boxer starts it when
needed and stops it once no route is left; a proxy you started yourself is never stopped.

Anything on this machine can reach a forwarded port, including other users' processes and a
browser tab that is sent to a `localhost` URL. A dev server in the sandbox should not be treated
as private to the agent.

## Secrets

```toml
[env]
NODE_ENV = "development"       # configuration. Baked into the pack.

env_passthrough = ["CI"]       # read from the host at run time
secrets         = ["NPM_TOKEN"]# same, and never written anywhere
```

`env` is snapshotted into the environment pack, which persists on disk. Put anything you would not
want in a snapshot in the other two lists. They are resolved on the host at run time and passed to
the guest process; they are not stored in VM metadata or in any file boxer keeps.

`env_passthrough` is an explicit allowlist, `["CI"]` by default. No other host variable reaches the
guest.

Both lists are forwarded **by name**. On smolvm, boxer passes `--secret-env NPM_TOKEN=NPM_TOKEN`
and smolvm reads the value from its own environment, so the value never appears in an argument
vector (which `ps` shows to every process on the host). The container backends have no such flag:
the values go through an `--env-file` readable only by your user, deleted as soon as the command
returns.

They reach `setup` and `image_setup` as well as ordinary commands, so an install that needs a
registry token has it. They never reach the pack: the pack is a filesystem snapshot, and a variable
resolved per invocation is not in the filesystem.

## What boxer records

With no `[telemetry]` table and no `BOXER_TRACE`, boxer writes no log, no metrics and nothing to
the network. When enabled, [events](/docs/reference/events) carry scope names, harness names,
durations and outcomes. Command lines are left out unless you also set `record_commands = true`.

One local file is always written: after every command, boxer writes
`$XDG_STATE_HOME/boxer/runs/<scope>.json`, mode 0600, holding that command verbatim, its exit
code, and a bounded tail of its output. `boxer capsule new` captures it and `boxer status --json`
reports it. `record_commands` does not gate it, because that setting guards the event sink (a file
or an OTLP endpoint, either of which can be shipped off the host). You can delete the directory at
any time; boxer reads it only to report.

Nothing leaves the machine unless you set an `endpoint`, which only a binary built with
`-tags otel` can use; the default build contains no exporter.

## Reporting a vulnerability

Privately, through [GitHub's private vulnerability
reporting](https://github.com/BarakChamo/boxer/security/advisories/new). Expect an acknowledgement
within three working days and a fix or a plan within fourteen. Until 1.0 only the latest release
is supported; from 1.0, the latest minor of the current major.
