---
title: Scopes and packs
description: How boxer decides which sandbox a command runs in, and how it caches built environments.
---

A **scope** is the identity of one sandbox: it decides which sandbox a command runs in. A **pack**
is a cached snapshot of a built environment: it decides whether a new sandbox has to be built. An
unexpected new sandbox, a missing one, or a setup step that ran again is usually one of these two.

## Scope

A scope is a name derived from the working directory and, for finer isolation, the agent's session
or subagent id.

```
sb-7e1852e4a3c3
```

`sb-` plus twelve hex characters of a SHA-256. It is also the sandbox's name on the backend. What
goes into the hash is set by `isolation`:

| `isolation` | Hashed | One VM per |
| --- | --- | --- |
| `repo` | the git common directory | repository, all worktrees together |
| `worktree` (default) | the worktree's root path | worktree |
| `session` | the worktree root and the session id | agent session |
| `subagent` | the worktree root, the session id and the agent id | subagent |

`worktree` is the default because orchestrators already create one worktree per task. Parallel
agents get separate sandboxes with no extra setup, and a sandbox's lifetime follows a worktree's.

### Degradation

`session` and `subagent` need an id the harness supplies. Not every harness supplies one, and one
configuration may be read by several harnesses.

```toml
isolation     = "session"
on_missing_id = "degrade"    # degrade | fail
```

`degrade` falls back one step (subagent to session, session to worktree) and prints a warning.
`fail` refuses to run.

### Placement is part of the key

Running the harness inside the guest ([inside mode](/docs/guides/inside)) and outside it produce
two different scopes for the same worktree, because one sandbox carries the harness and the other
does not.

## Packs

A pack is a snapshot of a guest after `image_setup` has run, taken with `smolvm pack create`. The
next sandbox with the same environment starts from the snapshot instead of rebuilding it. Packs
exist on smolvm only; on other [backends](/docs/concepts/backends) `image_setup` runs once per
sandbox.

### The key

A pack is keyed on the image plus a hash of everything that shaped it:

- `image_setup` — the commands that changed the guest
- `env` — the variables baked into it
- `mounts` — what else is attached
- `start` and `ready` — what a VM from this pack is expected to be running

Change any of them and the next sandbox builds a fresh pack.

`setup` is not in the key. It prepares the worktree, which no pack carries.

### `image_setup` versus `setup`

Putting a command in the wrong list is the most common configuration mistake.

```toml
image_setup = ["apt-get install -y libpq-dev"]   # changes the image → packed
setup       = ["npm ci"]                          # changes the worktree → not packed
```

A pack carries the guest's filesystem. The worktree is mounted from the host, so it is not in the
snapshot. Put `npm install` in `image_setup` and the second worktree starts from a pack that marks
the install done, with no `node_modules` in its worktree. Dependency installs belong in `setup`.
[Environment](/docs/guides/environment#dependencies) covers both lists and `[prep]`.

### Cache management

Packs are hundreds of megabytes each, and an environment that changes often leaves one per
version. Two settings bound the cache:

```toml
packs_keep_last = 5      # bound by count, not only by age
min_free_gb     = 5      # below this much free disk, skip packing
```

Below `min_free_gb`, boxer does not write a pack and says so; the next worktree runs its setup
again.

```sh
boxer up --rebuild     # drop this environment's pack and build it again
boxer gc               # unreferenced packs and idle sandboxes
boxer doctor           # what boxer currently costs on disk
```

Use `--rebuild` when something outside the key changed, such as a mutable base image tag or a
dependency resolved at install time.

### Packs you name

The packs above are a cache boxer manages. A named pack is one you manage:

```sh
boxer pack save base     # snapshot this sandbox as it stands
boxer pack ls
boxer pack use base      # recreate this scope's sandbox from it
boxer pack rm base
```

Use one for a guest that took real time to prepare: a toolchain assembled by hand, a state to
return to before a risky upgrade, or a base several worktrees should start from.

`gc` never touches a named pack. The automatic cache is swept by age and count.

<Callout>
A named pack is a filesystem snapshot: what is installed, not what is running. smolvm cannot
checkpoint RAM on a machine with a host mount, and boxer always mounts the worktree. The nearest
live snapshot is a [fork](/docs/guides/forking).
</Callout>

## Reading the current state

```sh
boxer status     # this scope: state, image, ports, mount
boxer ls         # every sandbox, with the worktree each is keyed to
boxer doctor     # the resolved scope, and why it is that one
```

When a sandbox is not the one you expected, run `boxer doctor`. It prints the isolation in force,
the resolved scope, and whether resolution degraded.

### Names

A scope key is a hash so that it is a legal machine name whatever the worktree path contains. For
readability, boxer also derives two words from the same hash and prints them beside it:

```console
NAME               SCOPE            STATE     ISOLATION  WORKTREE
swift-crab         sb-7e1852e4a3c3  running   worktree   /Users/me/src/demo
```

The name is computed from the key and never stored, so the same worktree always gets the same
words. Two keys can share a name; the key is always printed beside it. `--scope` accepts either
form.
