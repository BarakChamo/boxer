title: Backends
description: smolvm, Apple container, docker and podman compared by isolation boundary, enforced features and start-up time.

A backend is the runtime that runs the sandbox. boxer drives four. They differ in isolation
boundary, in what boxer can enforce through them, and in start-up time.

```toml
backend = "smolvm"     # smolvm | container | docker | podman
```

`BOXER_BACKEND` overrides it for one command. `boxer doctor` prints the backend you have with its
boundary first, and `boxer backends` compares every installed one.

## The boundary

| backend | what a sandbox is | boundary |
| --- | --- | --- |
| `smolvm` (default) | a microVM | **a kernel per sandbox** |
| `container` (Apple, macOS 26 on Apple Silicon) | a lightweight VM per container | **a kernel per sandbox** |
| `docker` | a container | one kernel shared by every sandbox on the machine |
| `podman` | a container | one kernel shared by every sandbox on the machine |

On a Mac, docker and podman run their containers inside one Linux VM, so "shared kernel" means
shared between sandboxes, not with macOS. On Linux they share the host's kernel.

An escape from a microVM lands in one guest. An escape from a container lands in the kernel every
other sandbox on that machine uses. boxer's threat model is a careless agent, not a hostile one
(see the [security model](/docs/concepts/security)); if containment is why you use boxer, keep a
kernel-per-sandbox backend.

## What each can do

Generated from the backends' code with `go test ./internal/vm -run CapabilityMatrix -v`:

| backend | egress allowlist | environment cache (packs) | fork | egress log | secrets off argv | ownership by label |
| --- | --- | --- | --- | --- | --- | --- |
| `smolvm` | yes | yes | yes | yes | yes | yes |
| `container` | — | — | — | — | yes | yes |
| `docker` | — | — | — | — | yes | yes |
| `podman` | — | — | — | — | yes | yes |

When a backend lacks a feature, boxer refuses with an error that names it, rather than
approximating:

- **Egress allowlist.** `network.mode = "allowlist"` is the default, and container runtimes offer
  only no network or full network. On those backends boxer refuses the default and the error gives
  the fix: set `network.mode` to `"off"` or `"on"`.
- **Packs** ([environment cache](/docs/concepts/scopes-and-packs#packs)). Without them,
  `image_setup` runs once per sandbox rather than once per host.
- **Forking.** `boxer fork` needs copy-on-write VM branching, which only smolvm has.

Everything else (hooks, shims, the MCP server, tasks, URLs, devcontainer support, `[prep]`, cache
mounts) works the same on all four. The smoke suite runs the same cells on each and skips, by
name, only those a backend's capabilities rule out.

## What each costs

Time for a Next.js dev server to answer HTTP 200, measured one backend at a time on a wiped host,
three samples each, 2 vCPU and 4 GB per sandbox, on a 10-core Apple Silicon Mac:

| backend | one worktree | three worktrees at once |
| --- | ---: | ---: |
| `podman` | **3.6 s** | 25.9 s |
| `docker` (OrbStack) | 4.5 s | **21.5 s** |
| `container` | 8.2 s | 25.6 s |
| `smolvm` | 8.5 s | 27.3 s |

The two kernel-per-sandbox backends land within 0.3 s of each other, so the ~4.6 s gap is the
cost of a kernel per sandbox, not of smolvm. At three worktrees the spread falls to 27%: three
Next.js compiles saturate the cores and the sandbox stops being the bottleneck. The cost is at
start-up only. A warm command in an existing sandbox takes 30–50 ms on all of them (31 ms measured
on smolvm, 36–51 ms on docker). Method and caveats: [Benchmarks](/docs/evals/benchmarks).

There is no memory column: the whole-host measurement varied twofold within a single
configuration.

## Choosing

- **Default:** `smolvm`. The only backend that enforces the egress allowlist, caches environments
  as packs, and forks.
- **A kernel per sandbox from ordinary OCI images, on macOS 26:** `container`.
- **You already run docker or podman, or you are on Linux without KVM:** `docker` or `podman`,
  with `network.mode` set explicitly. The sandboxes share a kernel.
- **Many short-lived sandboxes where start-up time dominates:** a container backend starts one
  about 4 s sooner.

## Known runtime problems

`boxer backends` checks for the ones it can detect.

- **podman on the `libkrun` provider cannot bind-mount host paths**, so no worktree can be mounted.
  Use the `applehv` provider on a Mac (`CONTAINERS_MACHINE_PROVIDER=applehv podman machine init`).
  A machine created under one provider is also invisible to `podman machine` commands run under
  another.
- **Apple `container` needs its service and a kernel.** `container system start`, then
  `container system kernel set --recommended`. A missing kernel shows up as every create failing.
- **OrbStack can give a new container a stale mount** when the same worktree path was removed and
  added again moments earlier, as an orchestrator does when it reuses a task name. boxer writes
  through the mount before running anything, and recreates the sandbox once if that fails.
- **SELinux denies an unlabelled bind mount** on Fedora, RHEL and CoreOS: the guest sees
  `Permission denied` on `/workspace`. When boxer runs on a Linux host with SELinux enforcing, it
  adds the shared relabel (`:z`) to every mount on docker and podman, which relabels the worktree
  and the package caches as container-shared on the host. It never does this on macOS.
- **Rootless podman maps you to the container's root**, so a non-root `user` (a devcontainer's
  `remoteUser`, for example) sees the worktree as root's and cannot write it. boxer notices, reads that
  user's uid from the image, and recreates the sandbox once with `--userns=keep-id` so the user is
  you; files it writes are owned by you on the host.
- **podman's storage can start failing with `input/output error` on overlay mounts** after heavy
  use, from the Mac client and inside the VM alike. `podman machine stop && podman machine start`
  cleared it without losing anything; `boxer backends --probe` shows it.
- **A runtime's own errors look like exit codes.** "No such container" exits 1, "OCI runtime exec
  failed" 127. boxer reads the runtime's message and reports a boxer error instead, so a command
  that never ran is not reported as a failed command.

```sh
boxer backends            # installed, answering, how many sandboxes, what each can enforce
boxer backends --probe    # create, use and delete a real sandbox on each
```

## Not supported

**Firecracker** needs `/dev/kvm`, which macOS does not have, and its maintainers declined a
Virtualization.framework port. **Docker Sandboxes (`sbx`)** has a per-host allowlist but no labels
on any object and no way to inspect a sandbox, so boxer cannot prove which sandboxes it owns. **Remote backends** such as Vercel
Sandbox copy the workspace rather than mounting it, which no backend here does yet.
