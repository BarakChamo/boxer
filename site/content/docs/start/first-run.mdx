title: Your first sandbox

## The first command creates the sandbox

```console
$ cd ~/code/myapp
$ boxer run -c 'echo hello from $(uname -s)'
hello from Linux
```

On that first command boxer:

1. Resolved the **scope**: the git worktree you are in. One worktree, one sandbox.
2. Read `boxer.toml` if there is one, and otherwise picked an image from the repository's lockfiles.
3. Created the sandbox with the worktree mounted at `/workspace`.
4. Ran the command and streamed its output back.

Your working directory maps into the mount: `boxer run` from `src/` runs in `/workspace/src`, so
relative paths work. Absolute host paths do not. To change the guest path, set `mount_at`;
[inside mode](/docs/guides/inside) mounts at the host path so absolute paths match on both sides.

Later commands in the same worktree reuse the sandbox. On smolvm, when `boxer.toml` has
`image_setup`, boxer also snapshots the prepared guest as an **environment pack**, and the next
worktree starts from it instead of repeating the setup. [Scopes and
packs](/docs/concepts/scopes-and-packs) covers what invalidates one.

## Seeing what exists

```sh
boxer ls          # boxer sandboxes on the configured backend (-A: every backend)
boxer status      # this worktree's sandbox: state, image, ports, mount
boxer doctor      # the resolved configuration, and what boxer is using on disk
```

`boxer logs` reads the event log, which is off until you set `[telemetry] enabled = true` in
`boxer.toml`.

## Removing it

<Callout type="warn">
`boxer down` **deletes** this worktree's sandbox; `boxer down --all` deletes every one. The worktree
on the host is untouched, but anything installed in the guest is gone, and the next command
provisions again.
</Callout>

```sh
boxer gc          # sandboxes whose worktree is gone, idle sandboxes, unreferenced packs
boxer gc --all    # also every stopped sandbox and every unreferenced pack, whatever their age
boxer gc --dry-run
```

[Managing sandboxes](/docs/guides/managing) covers `boxer stop`, `boxer rm` and the rest.
