```sh
boxer install claude-code     # or: codex, copilot, kimi, opencode, gemini-cli, grok, pi, dsh
boxer install all             # every harness this repository can see
boxer install codex --user    # the user layer instead, for harnesses that will not read a project one
```

`boxer install` picks the strongest integration the harness supports and writes exactly the files
that harness reads. Nothing is global: the files land in the repository, so a worktree carries its
own integration and a clone of it does too.

**Commit what it writes.** A worktree is cut from a branch, so an integration that is not in the
branch is not inherited — which is how an orchestrator's task ends up unsandboxed.

```sh
boxer install claude-code
git add .claude .mcp.json && git commit -m 'boxer'
```

## What lands where

| Harness | File | Level |
| --- | --- | --- |
| Claude Code | `.claude/settings.json`, `.mcp.json`, `.claude/skills/boxer/` | hooks, rewrite |
| Codex | `.codex/hooks.json`, `.agents/skills/boxer/` | hooks, rewrite |
| Copilot CLI | user-scope hooks | hooks, rewrite |
| OpenCode | `.opencode/plugin/`, `opencode.json` | plugin |
| Gemini CLI | `.gemini/settings.json` | hooks |
| Kimi Code | `.kimi-code/mcp.json` | tool |
| Grok, pi, DSH | per-harness config | varies |
| fx | nothing; it has no integration point | inside mode only |

Run `boxer doctor` afterwards. It lists the integrations it can see and warns about the ones that
are present but will not hold.

**fx is the exception.** It has no hooks, its shell cannot be denied headlessly, and it resolves
commands past a PATH shim, so outside the guest there is nothing for boxer to hold onto and
`boxer install` has nothing to write. Run it inside instead — with the caveat that only one of its
two evaluated cells scores 100%; see [Support, measured](/docs/evals/results):

```sh
boxer shell fx
```

A harness boxer has never heard of has the same ladder: register `boxer mcp` for the skill and the
tool, try shims, and fall back to [inside mode](/docs/guides/inside) if the binary can be
installed in the guest.

<Callout type="warn">
**Codex has two traps, and boxer can only handle one of them for you.**

It resolves project configuration to the **main repository**, not the worktree you are in. When
you install from a linked worktree, boxer writes its hooks to both; otherwise Codex never reads
them and every command runs on the host. That one is handled.

The other is trust. A project `.codex/hooks.json` loads only when the project layer is trusted,
and some launchers pass no trust bypass. Where you cannot rely on the project layer being trusted
— under an orchestrator, or in `codex exec` without `--dangerously-bypass-hook-trust` — install
at user scope instead, which needs no trust:

```sh
boxer install codex --user      # inline [hooks] in ~/.codex/config.toml
```

`boxer doctor` inside the worktree is how you confirm which one took.
</Callout>

## Five ways in, and they stack

Harnesses differ in what they let a third party do. boxer has five integration levels, and
whichever ones your harness supports are active at once.

1. **MCP server and skill.** A `boxer_run` tool and a skill telling the agent that shell commands
   here go through boxer. Works everywhere, enforces nothing.
2. **Hooks.** boxer inspects each shell call and rewrites intercepted commands to run in the guest.
   The agent never sees a refusal. This is enforcement.
3. **Plugins.** OpenCode loads a TypeScript plugin that does the same job in-process.
4. **PATH shims.** Files named after the programs you intercept, which re-run themselves in the
   guest. No harness cooperation at all.
5. **Inside mode.** The harness itself runs in the VM. Nothing to intercept, because there is no
   host side.

[How it works](/docs/guides/how-it-works) covers when each one applies and what it costs.

## Running someone else's MCP server in the sandbox

Some MCP servers have to sit next to the code — one that talks to a running dev server has to be
wherever that server is. `boxer run` is a clean stdio pipe, which is all an MCP client needs. See
[MCP server](/docs/reference/mcp#running-someone-elses-mcp-server-in-the-sandbox).
