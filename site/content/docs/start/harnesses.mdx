title: Connect your harness
description: One command per coding agent, what it writes, and what to commit.

A harness is the coding agent's CLI: Claude Code, Codex, Gemini CLI and so on. `boxer install`
writes the configuration that harness reads so its shell commands go through boxer.

```sh
boxer install claude-code     # or: codex, gemini-cli, opencode, grok, kimi, pi, dsh
boxer install all             # all eight of those
boxer install copilot --user  # Copilot has no project layer; this writes ~/.copilot
boxer install codex --user    # user layer instead of the project one (claude-code, codex, copilot)
```

`boxer install` picks the strongest integration the harness supports and writes only the files
that harness reads. Apart from `--user`, the files land in the repository, so a worktree and a clone
carry the integration with them. It also prints notes for any step it cannot do for you.

To install only the skill, or the plugin package through `npx plugins`, see
[Skills and plugins](/docs/guides/skills-and-plugins). Neither enforces on its own.

**Commit what it writes.** A worktree is cut from a branch, so an integration that is not in the
branch is not in the worktree, and an orchestrator's task there runs unsandboxed.

```sh
boxer install claude-code
git add .claude .mcp.json && git commit -m 'boxer'
```

## What lands where

| Harness | Files | Level |
| --- | --- | --- |
| Claude Code | `.claude/settings.json`, `.mcp.json`, `.claude/skills/boxer/`, `.claude/agents/boxed.md` | hooks, rewrite |
| Codex | `.codex/hooks.json`, `.agents/skills/boxer/` | hooks, rewrite |
| Copilot CLI | `~/.copilot/hooks/boxer.json`, `~/.copilot/mcp-config.json`, `~/.copilot/skills/boxer/` (`--user` only) | hooks, rewrite |
| OpenCode | `.opencode/plugins/boxer.ts`, `opencode.json`, `AGENTS.md` | plugin |
| Gemini CLI | `.gemini/settings.json`, `GEMINI.md` | hooks |
| Kimi Code | `.kimi-code/mcp.json`, `.agents/skills/boxer/` | tool |
| Grok | `.grok/hooks/boxer.json`, `.mcp.json`, `.agents/skills/boxer/` | hooks, rewrite |
| pi | `.pi/extensions/boxer.ts`, `AGENTS.md` | extension, rewrite |
| DSH | `.dsh/cordis.patch.yml`, `.dsh/hooks.json`, `.agents/skills/boxer/` | tool |
| fx | nothing; it has no integration point | inside mode only |

Then run `boxer doctor`. It lists the integrations it can see and warns about any that are present
but will not hold.

Some harnesses need one more step, which `boxer install` prints as a note:

- **Claude Code**: approve the `boxer` MCP server from `.mcp.json` the first time you open the
  repository. The hooks load without a prompt once the folder is trusted.
- **Codex**: add the MCP server to `.codex/config.toml`, and trust the project hooks (see below).
- **Kimi**: its hooks live only in the user config; append the printed block to
  `~/.kimi-code/config.toml` and set `[harness.kimi] mode = "tool"` in `boxer.toml`. PATH shims
  also work in Kimi's shell ([Enforcement](/docs/guides/enforcement#path-shims)).
- **DSH**: start it with `--patch .dsh/cordis.patch.yml`, and set `[harness.dsh] mode = "tool"`.
- **Grok** and **pi**: trust the project folder once, or project hooks and extensions do not load.

<Callout type="warn">
**Codex** reads project configuration from the main repository, not the linked worktree. Run from a
linked worktree, `boxer install codex` writes its hooks to both. Codex also loads project hooks only
once they are trusted. Under an orchestrator, or in `codex exec` without
`--dangerously-bypass-hook-trust`, use `boxer install codex --user`, which needs no trust.
</Callout>

**fx** has no hooks, its shell cannot be denied headlessly, and it resolves commands past a PATH
shim, so `boxer install` has nothing to write. Run it inside the sandbox instead.

```sh
boxer shell fx
```

For a harness boxer does not know, register `boxer mcp` as an MCP server for the `boxer_run` tool,
try [PATH shims](/docs/guides/enforcement#path-shims), and fall back to [inside mode](/docs/guides/inside) if
the harness can be installed in the guest.

## Integration levels

boxer has five ways to route a harness's commands. Whichever ones a harness supports are active at
once.

1. **MCP server and skill.** A `boxer_run` tool, and a skill telling the agent that shell commands
   here go through boxer. Works everywhere; enforces nothing.
2. **Hooks.** boxer inspects each shell call and rewrites intercepted commands to run in the guest.
3. **Plugins.** OpenCode loads a TypeScript plugin that does the same in-process.
4. **PATH shims.** Files named after the intercepted programs, which re-run themselves in the
   guest. Needs no harness support.
5. **Inside mode.** The harness itself runs in the VM, so there is nothing on the host to intercept.

[How it works](/docs/guides/how-it-works#how-a-command-reaches-the-sandbox) compares them, and
[Enforcement](/docs/guides/enforcement) has the details.

## Running someone else's MCP server in the sandbox

An MCP server that talks to a dev server has to run where that server is. `boxer run` is a clean
stdio pipe, so it can launch one in the guest. See
[MCP server](/docs/reference/mcp#running-someone-elses-mcp-server-in-the-sandbox).
