```sh
boxer install claude-code     # or: codex, copilot, kimi, opencode, gemini-cli, grok, pi, dsh
boxer install all             # every harness this repository can see
```

`boxer install` picks the strongest integration the harness supports and writes exactly the files
that harness reads. Nothing is global: the files land in the repository, so a worktree carries its
own integration and a clone of it does too.

## What lands where

| Harness | File | Level |
| --- | --- | --- |
| Claude Code | `.claude/settings.json`, `.mcp.json`, `.claude/skills/boxer/` | hooks, rewrite |
| Codex | `.codex/hooks.json`, `.agents/skills/boxer/` | hooks, rewrite |
| Copilot CLI | user-scope hooks | hooks, rewrite |
| OpenCode | `.opencode/plugin/`, `opencode.json` | plugin |
| Gemini CLI | `.gemini/settings.json` | hooks |
| Kimi Code | `.kimi-code/mcp.json` | tool |
| Grok, pi, DSH | per-harness config | varies |

Run `boxer doctor` afterwards. It lists the integrations it can see and warns about the ones that
are present but will not hold.

<Callout type="warn">
Codex resolves project configuration to the **main repository**, not the worktree you are in. When
you install from a linked worktree, boxer writes its hooks to both — otherwise Codex never reads
them and every command runs on the host. `boxer install` does this for you; it is worth knowing
because it is invisible otherwise.
</Callout>

## Five ways in, and they stack

Harnesses differ in what they let a third party do. boxer has five integration levels, and
whichever ones your harness supports are active at once.

1. **MCP server and skill.** A `boxer_run` tool and a skill telling the agent that shell commands
   here go through boxer. Works everywhere, enforces nothing.
2. **Hooks.** boxer inspects each shell call and rewrites intercepted commands to run in the guest.
   The agent never sees a refusal. This is enforcement.
3. **Plugins.** OpenCode loads a TypeScript plugin that does the same job in-process.
4. **PATH shims.** Files named after the programs you intercept, which re-run themselves in the
   guest. No harness cooperation at all.
5. **Inside mode.** The harness itself runs in the VM. Nothing to intercept, because there is no
   host side.

[How it works](/docs/guides/how-it-works) covers when each one applies and what it costs.

## Running someone else's MCP server in the sandbox

Some MCP servers have to sit next to the code — `next-devtools-mcp` talks to a running Next.js dev
server, so it has to be wherever that server is. `boxer run` is a clean stdio pipe, which is all an
MCP client needs:

```json
{
  "mcpServers": {
    "next-devtools": {
      "command": "boxer",
      "args": ["run", "--", "npx", "-y", "next-devtools-mcp@latest"]
    }
  }
}
```

The harness stays on the host and talks to a tool inside the guest. Nothing bridges, and the tool
does not know boxer exists.
