## Running things

| Command | What it does |
| --- | --- |
| `boxer run -c '<shell>'` | Run a shell line in the sandbox |
| `boxer run -- <prog> [args]` | Run a program, without a shell |
| `boxer run --task <name>` | Run a command this repository declared in `[tasks]` |
| `boxer run --tty -- <prog>` | Allocate a terminal in the guest even when stdin is not one |

`--task` is the one to reach for from an agent: it names a command the repository declared, so
nothing depends on the intercept list recognising a line a model composed.

`--tty` matters for anything that drives an interactive shell. boxer also buffers input written
before the sandbox has attached, so a caller that configures its shell immediately after starting
it does not lose that configuration to the seconds a VM takes to come up.

## Lifecycle

| Command | What it does |
| --- | --- |
| `boxer up` | Create and start this scope's sandbox |
| `boxer up --detach` | Provision in the background and return at once |
| `boxer up --rebuild` | Drop the environment pack and build it again |
| `boxer up --recreate` | Delete and recreate the VM |
| `boxer down` | Delete this scope's sandbox |
| `boxer down --all` | Every sandbox boxer owns |
| `boxer down --scope NAME` | One by name, without resolving a worktree |

## Looking

| Command | What it does |
| --- | --- |
| `boxer status` | This scope's sandbox. Exit 0 running, 3 stopped, 4 absent |
| `boxer ls [--resources]` | Every sandbox, optionally with cpu and memory |
| `boxer doctor` | The resolved configuration, and what is wrong with it |
| `boxer brief` | The agent-facing summary: mount, mode, intercept, tasks |
| `boxer tasks` | The command lines declared in `[tasks]` |
| `boxer logs [-n N]` | The event log, when `[telemetry] sink = "file"` |
| `boxer watch` | Stream sandbox state changes as they happen |

`--json` on `ls`, `status`, `down`, `gc` and `doctor` prints one object or array. See
[JSON output](/docs/reference/json).

## Reclaiming

| Command | What it does |
| --- | --- |
| `boxer gc` | Sandboxes whose worktree is gone, idle sandboxes, unreferenced packs |
| `boxer gc --dry-run` | What it would delete |
| `boxer gc --all` | Every sandbox boxer owns, running or not |

## Integrating

| Command | What it does |
| --- | --- |
| `boxer install <harness>` | Write this repository's hooks, tool and skill for one harness |
| `boxer install all` | Every harness this repository can see |
| `boxer install <harness> --user` | Write the user-scope files instead |
| `boxer install git` | A post-checkout hook that warms each new worktree |
| `boxer install conductor` | `.conductor/settings.toml` with harness shims and a warm-up script |
| `boxer hook <harness>` | The hook entry point itself; reads JSON on stdin |
| `boxer mcp` | An MCP server exposing `boxer_run` and `boxer_status` |
| `boxer package plugin\|<harness>\|all` | Render the Agent Plugins package |

Harnesses: `claude-code`, `codex`, `gemini-cli`, `grok`, `kimi`, `dsh`, `opencode`, `pi`,
`copilot`.

## Shims

| Command | What it does |
| --- | --- |
| `boxer shim install [dir]` | One file per entry in `intercept` |
| `boxer shim install --harness a,b [dir]` | Files named after harness binaries, running `boxer shell` |
| `boxer shim install --shell [dir]` | `boxer-bash`: a shell that runs in the sandbox |

boxer removes its own shim directories from `PATH` before starting anything, so a shim can never
be resolved by boxer itself. Without that, a `uname` shim turns into `boxer run -- uname` inside a
boxer that is already working on the same sandbox.

## Inside mode

| Command | What it does |
| --- | --- |
| `boxer shell <harness> [-e K=V] [-- args]` | Run the harness itself in the sandbox |
| `boxer acp <harness>` | Run the harness's ACP server in the sandbox, stdio piped |

Harnesses: `claude`, `codex`, `fx`, `gemini`, `kimi`, `opencode`, `pi`, `grok`, `copilot`.

## Identity

`up`, `run`, `down`, `status` and `doctor` take `--harness NAME`, `--session ID` and `--agent ID`.
They matter when `isolation` is keyed to something other than the worktree.
