title: Benchmarks
description: What boxer costs against the alternatives and across its own backends, with the method and the withdrawn claims.

Every number here was measured on one machine, an Apple Silicon Mac with 10 cores and 24 GB. The
benchmark scripts are in `bench/` in the repository; each writes its raw results beside it, and
`bench/README.md` has the full method. A number measured only once is labelled a single sample.

## A command in a running sandbox

`make bench`, a no-op and a set of ordinary workloads, into an already-running sandbox:

| | no-op |
| --- | ---: |
| seatbelt (the sandbox Claude Code and Codex use on macOS) | ~8 ms |
| **`boxer run`**, smolvm | **31 ms** |
| `docker exec` into a running container | 32 ms |
| `docker run`, a fresh container per command | 253 ms |

- **boxer is level with a warm container**, within 4% on every workload that is not I/O-bound.
- **It beats a container per command by about 8x**, because the sandbox per worktree stays warm.
- **Seatbelt is faster**, and isolates something different: a syscall filter around a host process,
  not another kernel.
- **The mount costs.** A recursive grep is 2.3x a warm container, a 200-file write 2.6x. That is
  virtiofs, and it is the one cost here inherent to the boundary.
- **boxer's overhead is fixed per command**: +13 to +22 ms over raw `smolvm machine exec` on every
  workload, most of it starting the `smolvm` process. boxer's own code is under 1 ms of it.
- The rewrite hook every intercepted command goes through takes 3 ms.

## Starting a development stack

`make bench-devserver`: time for a Next.js dev server to answer HTTP 200, with the image, the
lockfile, the npm cache and the allocation held equal between contenders.

| | start a session (deps installed) | install dependencies |
| --- | ---: | ---: |
| no sandbox | 6.8 s | — |
| **boxer**, smolvm | **7.6 s** | 9.2 s |
| OrbStack (a container) | 10.8 s | 5.2 s |

Starting a session is paid every time; boxer is 0.8 s over running with no sandbox. Installing is
boxer's weak row, because the guest writes through the mount. [`[prep]`](/docs/reference/configuration#preparing-the-worktree-before-the-sandbox-starts)
and the host package-cache mounts exist to move that work out of the guest.

## Several sandboxes at once

`bench/parallel-clean.sh`, at Vercel Sandbox's default shape — 2 vCPU and 4 GB each — with one
linked worktree per sandbox and every cell measured from a wiped host:

| sandboxes | boxer, ready | OrbStack, ready |
| ---: | ---: | ---: |
| 1 | **7.6 s** | 10.2 s |
| 3 | 22.3 s | **18.8 s** |
| 5 | **26.3 s** | 27.1 s |

Past the first sandbox the time is dominated by Next.js compiling on ten shared cores. One and
three are single samples; five is the median of three to four.

## Across boxer's backends

`bench/backends.sh`, one backend at a time, alone on the host, three samples each:

| backend | boundary | one worktree | three worktrees |
| --- | --- | ---: | ---: |
| podman | shared kernel | **3.6 s** | 25.9 s |
| docker | shared kernel | 4.5 s | **21.5 s** |
| Apple `container` | kernel per sandbox | 8.2 s | 25.6 s |
| smolvm | kernel per sandbox | 8.5 s | 27.3 s |

The two kernel-per-sandbox backends agree within 0.3 s, and the two shared-kernel ones within
0.9 s, so the ~4.6 s gap is the cost of the boundary rather than of one implementation. At three
worktrees the spread falls to 27%. Shared-kernel backends are also near-deterministic (docker
±0.2 s over six cells) where microVMs are not (smolvm ±2.3 s at one worktree).

## Features

Measured interleaved, on against off, five pairs:

| | `boxer up` | warm `boxer run` |
| --- | ---: | ---: |
| `[urls]` off | 289 ms | 49 ms |
| `[urls]` on | 322 ms | 51 ms |

Registering a URL runs alongside setup, so most of it is hidden. With `[urls]` off, nothing runs.

## Memory, and why there is no ratio

A sandbox serving a Next.js dev server touches about **1.2 GB inside the guest**, 642 MB of it
node's own heap, and does not grow to fill a larger allocation. That replicates across runs.

What it costs the host compared with a container is not established. The whole-host measurement
varied up to 2.1x within a single configuration (halving each guest's memory produced both the
lowest and the highest figure), so any ratio drawn from it is within the noise. A microVM per
worktree costs more than a shared kernel, by a kernel, a guest userland and a page cache each; how
much more on this workload is unmeasured.

## Withdrawn

Three earlier claims did not survive repetition:

- **"About 243 MB per sandbox, crossover at six."** Measured on sandboxes running nothing. One
  serving a dev server costs about a gigabyte, most of it node.
- **"Four times OrbStack's memory at five sandboxes."** The harness ran every cell in one process,
  so the container runtime's VM was already grown and it was charged only for marginal growth. From
  a wiped host the same cell read 2.2–2.9 GB, not 501 MB.
- **"Halving the guest allocation saves memory."** It produced the widest spread measured.

Each was a single sample that matched an expectation.

## The caveats that remain

- **One host, one architecture.** On a Mac, `docker exec` crosses a VM boundary too; on a Linux host
  every container row would be cheaper and the comparison would change. This is the largest caveat.
- **Cache state dominates cold start.** A first run pulls the image; every figure above is warm
  unless it says otherwise.
- **Benchmarks gate nothing.** Whether boxer works is covered by the
  [evaluation tiers](/docs/evals/strategy).
