---
title: Why there are evaluations
description: What boxer claims, and the evaluation tiers that check each claim.
---

boxer's claims are about behaviour: *this harness's commands run in the sandbox*, *this integration
level holds*, *a worktree's sandbox is its own*, *an agent finds its own server*. Unit tests cannot
establish these, because they depend on a real coding agent running against a real runtime. The
evaluation tiers test them, and every result is published with the conditions it was measured under.

| Tier | What it asks | Cost |
| --- | --- | --- |
| smoke | Does every configuration path work on each backend? | free, minutes |
| `t1` | Does each integration work, with a scripted model? | free, fast |
| `t2` | The same, with real models | cents |
| `adherence` | When boxer only *asks*, how often do agents comply? | cents |
| `flow` | Can an agent develop against a dev server in the sandbox? | cents |
| `sdlc` | Twelve development lifecycles in parallel worktrees | ~$0.30 |
| `matrix` | The same workload at every integration level | ~$2 |

An integration level is how boxer routes a harness's commands into the sandbox (hook rewrite, shims,
running inside the guest, ...); see [Enforcement](/docs/guides/enforcement).

```sh
make smoke          # one backend; BOXER_BACKEND=docker make smoke for another
make eval-t1        # no credentials needed
make eval-matrix    # needs an AI Gateway key
```
