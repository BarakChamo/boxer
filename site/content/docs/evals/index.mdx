---
title: Why there are evaluations
description: What boxer claims, and how those claims are checked.
---

boxer's claims are behavioural: *this harness's commands run in the sandbox*, *this level of
integration holds*, *a worktree's sandbox is its own*, *an agent finds its own server*. None of that
can be established by unit tests, because the thing being tested is a real coding agent's behaviour
against a real runtime.

So there are evaluation tiers, and the results are published with the conditions that produced
them.

| Tier | What it asks | Cost |
| --- | --- | --- |
| smoke | Does every configuration path work on each backend? | free, minutes |
| `t1` | Does each integration work, with a scripted model? | free, fast |
| `t2` | The same, with real models | cents |
| `adherence` | When boxer only *asks*, how often do agents comply? | cents |
| `flow` | Can an agent develop against a dev server in the sandbox? | cents |
| `sdlc` | Twelve development lifecycles in parallel worktrees | ~$0.30 |
| `matrix` | The same workload at every integration level | ~$2 |

```sh
make smoke          # one backend; BOXER_BACKEND=docker make smoke for another
make eval-t1        # no credentials needed
make eval-matrix    # needs an AI Gateway key
```
