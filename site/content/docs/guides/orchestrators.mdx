---
title: Orchestrators
description: Tools that cut a worktree per task, and what boxer does about it.
---

An orchestrator opens a worktree for each task and starts a harness in it. Since boxer keys a
sandbox to the worktree, that is already the right shape: the sandbox appears with the worktree
and goes away with it.

What differs is how the harness gets launched, and therefore which integration level applies.

## Warm the sandbox first

```sh
boxer install git
```

This writes a `post-checkout` hook (honouring `core.hooksPath`) that runs `boxer up --detach` in
every worktree `git worktree add` creates, so the VM is warm before any harness opens it.

Any orchestrator that creates a worktree and launches into it wants this. The failure without it
is not a slow start but a broken session: T3 Code creates the worktree and starts the harness in
the same step, and its provider fails with `turn/setPermissionMode failed` while a cold VM boots
(reproduced three times, 32 to 39 seconds). With the hook, the same cell passes.

`boxer install all` leaves git configuration alone, so this one is opt-in and separate.

## T3 Code

Cuts a worktree and runs Claude Code in it. The project layer is inherited, so
`boxer install claude-code` — committed — is the whole integration.

```sh
boxer install claude-code
git add .claude .mcp.json && git commit -m 'boxer'
boxer install git                                    # warm each new worktree
```

The commit matters: an orchestrator cuts its worktree from a branch, so the integration has to be
in the branch to be inherited.

## Paperclip

Launches its harness over ACP with an environment of its own. The project layer is inherited the
same way, but boxer's trace variable is not, so `boxer doctor` inside the task worktree is how you
confirm it took.

## herdr

Drives a harness interactively in a terminal pane, which makes two things matter that do not
elsewhere:

- The harness is started by herdr, so there is no command line to put `--permission-mode` on.
  Grants have to live in project settings, and they must include `Skill` — boxer installs one, and
  using a skill is its own permission. A pane sitting on `Use skill "boxer"?` looks exactly like a
  hang.
- `terminal.default_shell` can point at `boxer shim install --shell`'s wrapper, which puts every
  pane's shell in the sandbox. This works for a person typing in a pane. herdr will not attach its
  own agent to such a pane — it identifies a pane by its foreground process, which is then `boxer`
  rather than a shell.

## Conductor

Conductor runs each harness's real binary against an ordinary git worktree, so there are two ways
in and the cheap one probably already works.

**Try the project layer first.** If Conductor inherits it like every other tool that uses real
worktrees, the ordinary install is the whole integration:

```sh
boxer install claude-code
git add .claude .mcp.json && git commit -m 'boxer'
```

**Otherwise, put the harness in the VM.**

```sh
boxer install conductor        # writes .conductor/settings.toml
```

That writes a managed block pointing `claude_code_executable_path` and friends at harness shims,
so Conductor spawns the shim, the shim runs `boxer shell <harness>`, and the harness itself runs
in the VM.

<Callout>
Conductor's local workspaces are GUI-only: it is a native app, not an Electron one, and its CLI
drives cloud workspaces, which run on Conductor's infrastructure where boxer has nothing to
sandbox. Verification is a ten-minute manual check rather than an automated one.
</Callout>

## Multica

Multica runs a daemon that cuts a worktree per issue. The integration is the inside path: point
its runtime profile at a boxer harness shim.

```sh
boxer shim install --harness claude ~/.boxer/shims
multica runtime profile create --command-name claude
multica runtime profile set-path claude ~/.boxer/shims/claude
```

Prefer the profile over `MULTICA_CLAUDE_PATH`: it is per-installation configuration rather than
per-process environment, so it survives a daemon restart and applies to every task the daemon
runs. Start the daemon from a shell with `boxer` on `PATH`.

<Callout type="warn">
Multica is the one orchestrator boxer has **not** verified end to end. Its daemon needs a
configured server, which the evaluation host did not have, so its cell is a checklist that reports
itself as skipped rather than a run that passed. The steps above follow from what the binary
reads; treat them as untested until you have run them.
</Callout>

## OpenHands

OpenHands lets you set the shell its terminal uses, which is the shell-substitution level: the
agent's entire terminal is the sandbox, with no boxer integration inside the harness.

```sh
boxer shim install --shell ~/.boxer/shims     # writes boxer-bash
```

Point the terminal tool's `shell_path` at it.
