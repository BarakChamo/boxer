---
title: Set up an orchestrator
description: "Set up boxer for tools that create a worktree per task: T3 Code, Paperclip, herdr, Conductor, Multica, OpenHands."
---

An orchestrator opens a worktree for each task and starts a harness in it. boxer keys a sandbox to
the worktree, so each task gets its own sandbox, and `boxer gc` removes it once the worktree is
gone. How the orchestrator launches the harness decides which
[integration level](/docs/guides/enforcement) applies.

| Orchestrator | Integration | Level | Evidence |
| --- | --- | --- | --- |
| T3 Code | committed project layer, or a harness shim as `binaryPath` | hook rewrite, or inside | matrix, 2 of 2 |
| Paperclip | committed project layer (Claude Code); `--user` layer (Codex) | hook rewrite | matrix, 2 of 2 |
| herdr | committed project layer; harness shims or `boxer-bash` optional | hook rewrite | matrix, 2 of 2 |
| Conductor | project layer, or `boxer install conductor` | hook rewrite, or inside | by hand |
| Multica | a runtime profile pointed at a harness shim | inside | untested |
| OpenHands | `boxer-bash` as the terminal's `shell_path` | shell substitution | matrix, 1 of 1 |

boxer must be on `PATH` where the orchestrator runs, since hooks and shims call it.

## Warm the sandbox first

```sh
boxer install git
```

This writes a `post-checkout` hook (honouring `core.hooksPath`) that runs `boxer up --detach` in
every worktree `git worktree add` creates, so the VM is booting before any harness opens it.

Use it with any orchestrator that creates a worktree and launches into it at once. Without it, T3
Code's provider fails with `turn/setPermissionMode failed` while a cold VM boots (32 to 39
seconds). `boxer install all` does not touch git configuration, so run this separately.

## Commit the project layer

T3 Code, Paperclip and herdr all start the harness in a worktree cut from a branch. The integration
must be in that branch, so commit it:

```sh
boxer install claude-code
git add .claude .mcp.json && git commit -m 'boxer'
```

A user-level plugin does not reach these harnesses. T3 Code and Paperclip launch each harness with a
config directory of their own (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`), and that directory does not carry
`~/.claude/plugins`. The project layer is the one every launcher reads.

## T3 Code

T3 Code cuts a worktree per thread and runs Claude Code in it. The committed project layer and
`boxer install git` are the whole integration.

To run the harness itself in the VM, write a harness shim and name it as the provider instance's
`binaryPath` in T3 Code's settings:

```sh
boxer shim install --harness claude
```

T3 Code spawns the shim, the shim runs `boxer shell claude`, and the harness runs
[inside](/docs/guides/inside). This path needs `boxer install git`.

## Paperclip

Paperclip launches its harness over ACP with a managed environment. `claude-agent-acp` loads the
project layer, so the committed `boxer install claude-code` is enough for Claude Code.

For Codex, use the user layer. Paperclip passes no hook-trust bypass, and it seeds its managed
`CODEX_HOME` from `~/.codex/config.toml`, not from `hooks.json`:

```sh
boxer install codex --user
```

Paperclip does not pass boxer's trace variable through, so run `boxer doctor` in the task worktree
to confirm the integration is active. Turn on isolated workspaces in Paperclip's experimental
settings, or every run shares the project checkout and one sandbox.

## herdr

herdr drives a harness interactively in a terminal pane. The pane inherits herdr's environment, so
the committed project layer applies.

- herdr starts the harness, so there is no command line to add `--permission-mode` to. Grant
  permissions in project settings, and include `Skill`, since using boxer's skill needs its own
  permission. A pane waiting on `Use skill "boxer"?` looks like a hang.
- To run the harness in the VM, put the directory from `boxer shim install --harness claude,codex`
  first on herdr's `PATH`. `herdr agent start --kind claude` then runs `boxer shell claude`.
- `terminal.default_shell` can point at `boxer-bash` (from `boxer shim install --shell`), which
  puts every pane's shell in the sandbox. This works for a person typing in a pane, but herdr will
  not attach its own agent to such a pane. It identifies a pane by its foreground process, which is
  then `boxer`.

`adapters/herdr/herdr-plugin.toml` in the repository adds a pane action that runs
`boxer shell claude` and warms the sandbox on `worktree.created`. Link it with
`herdr plugin link adapters/herdr`.

## Conductor

Conductor runs each harness's real binary against an ordinary git worktree.

**Try the project layer first.** If Conductor's sessions load project hooks, the committed
`boxer install claude-code` is the whole integration. Create a workspace, ask the agent to run
`uname -a`, and run `boxer ls`. An answer of `Linux` and a sandbox keyed to Conductor's worktree
mean it works.

**Otherwise, put the harness in the VM.**

```sh
boxer shim install --harness claude,codex,opencode
boxer install conductor        # writes .conductor/settings.toml
```

`boxer install conductor` points `claude_code_executable_path`, `codex_executable_path` and
`opencode_executable_path` at the shims in `~/.local/share/boxer/shims`, and sets a setup script
that runs `boxer up --detach && boxer doctor`. Conductor spawns the shim, and the harness runs
[in the VM](/docs/guides/inside).

The setup script warms each workspace's sandbox, so `boxer install git` is not needed here. The file
holds absolute paths to your shim directory, so it is specific to your machine: each developer runs
the two commands above rather than sharing one committed copy.

<Callout>
Conductor's local workspaces are GUI-only, and its CLI drives cloud workspaces where boxer has
nothing to sandbox, so this integration is verified by hand, not by the evals.
</Callout>

## Multica

Multica runs a daemon that creates a worktree per issue. Point its runtime profile at a boxer
harness shim, so the harness runs in the VM:

```sh
boxer shim install --harness claude ~/.local/share/boxer/shims
multica runtime profile create --command-name claude
multica runtime profile set-path claude ~/.local/share/boxer/shims/claude
```

Prefer the profile over `MULTICA_CLAUDE_PATH`, since it survives a daemon restart and applies to
every task. Start the daemon from a shell with `boxer` on `PATH`.

<Callout type="warn">
**Untested.** Multica's daemon needs a configured server, which the evaluation host did not have,
so its eval cell reports as skipped. These steps follow from what the binary reads.
</Callout>

## OpenHands

OpenHands lets you set its terminal's shell, so the agent's whole terminal can be the sandbox with
no boxer integration in the harness:

```sh
boxer shim install --shell ~/.local/share/boxer/shims     # writes boxer-bash
```

Point the terminal tool's `shell_path` at `~/.local/share/boxer/shims/boxer-bash`. For code that calls
`workspace.execute_command` directly, `adapters/openhands` has a `BoxerWorkspace`.

## Clean up

Orchestrators remove worktrees without telling boxer. `boxer gc` reclaims sandboxes whose worktree
is gone in the background. To do it now:

```sh
boxer rm --gone -A
```
