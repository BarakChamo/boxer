boxer is a CLI, but most of what it knows is available to a program. An orchestrator that opens a
worktree per task, a dashboard that shows what is running, an integration for a harness nobody has
written: all three are built from the same three entry points.

Pick by what you are writing:

| You are writing | Use |
| --- | --- |
| A Go program that owns sandbox lifecycle | [`pkg/boxer`](#go) |
| Anything else that needs to read state | [`--json`](#json) |
| An integration for a harness | [the CLI](#the-cli-as-an-interface) |

## Go

```go
import "github.com/BarakChamo/boxer/pkg/boxer"
```

The only importable package; everything else is under `internal/`. It is a thin facade with no
logic of its own, which is deliberate — behaviour lives in one place and the facade cannot drift
from it.

<Callout>
Experimental until 1.0, and covered by the stability contract from 1.0 onwards.
</Callout>

```go
b, err := boxer.Open(cwd, boxer.Options{Harness: "claude-code", SessionID: sid})
if err != nil {
    var be *boxer.Error
    if errors.As(err, &be) {
        log.Fatalf("%s (%s): %s", be.Reason, be.Cause, be.Fix)
    }
    log.Fatal(err)
}

for _, w := range b.Warnings() {
    log.Println("boxer:", w)   // main checkout, degraded isolation
}

if _, err := b.Ensure(true, false); err != nil {   // create if needed, then start
    log.Fatal(err)
}

code, err := b.Run(
    []string{"sh", "-c", "npm test"},
    boxer.RunOpts{Stdin: os.Stdin, Stdout: os.Stdout, Stderr: os.Stderr},
)
```

`Options` carries the harness name and the identity. Both may be empty; they matter when
`isolation` is keyed to something other than the worktree, and when a `[harness.<name>]` override
should apply.

### Handling refusals

Every refusal is a `*boxer.Error` with four fields: `Reason` and `Fix` for a person, `Cause` for a
program, and `Scope` for context. `Cause` is the stable one — match on it, not on the message.

`Run` returns `-1` with an error when `on_sandbox_unavailable = "passthrough"` and the sandbox
could not be provisioned. That is boxer handing the decision back: your caller decides whether to
fall back to the host. boxer will not make that choice silently.

### Host-wide operations

```go
machines, _ := boxer.List()          // every boxer-owned machine
_ = boxer.Stop("sb-7e1852e4a3c3")
_ = boxer.Delete("sb-7e1852e4a3c3")
t := boxer.LastUsed("sb-7e1852e4a3c3")
```

These take a machine name rather than a working directory, because a dashboard has names and the
worktree may already be gone.

## JSON

For anything that is not Go. `--json` on `ls`, `status`, `down`, `gc`, `doctor`, `brief`, `tasks`
and `logs` prints exactly one JSON document on stdout. Fields are added, never repurposed or
removed. See [JSON output](/docs/reference/json) for the shapes.

```sh
boxer ls --json --resources     # every sandbox, with live cpu and memory
boxer status --json             # this scope; exit 0 running, 3 stopped, 4 absent
boxer doctor --json             # the resolved configuration and every check
```

Exit codes carry the answer for `status`, so a health check does not have to parse anything.

### Watching instead of polling

```sh
boxer watch --json
```

One JSON object per line, per state change, as it happens — created, running, stopped, gone. A
dashboard reads this instead of polling `ls` on a timer.

## The CLI as an interface

An integration for a harness nobody has written is four commands, and none of them needs a
library.

```sh
boxer hook <harness>    # reads the harness's hook JSON on stdin, writes its dialect back
boxer mcp               # boxer_run and boxer_status over stdio
boxer brief --json      # the mount, mode, intercept list and tasks, for a prompt
boxer run -c '<line>'   # the escape hatch: a shell line in the guest
```

`boxer hook` already speaks nine dialects. If the harness you are integrating resembles one of
them, adding a row is a smaller change than writing a bridge — see
[Adding a harness](https://github.com/BarakChamo/boxer/blob/main/docs/adding-a-harness.md).

If it resembles none of them, `boxer run` is a clean stdio pipe with the guest's exit code, and
that is enough to build on.

## Worth knowing before you build

**Provisioning is idempotent and lazy.** `Ensure` and `boxer up` both no-op on a running sandbox.
Call them freely rather than tracking state yourself.

**boxer strips its own shim directories from `PATH`.** It does this before starting anything, so
a shim can never be resolved by boxer itself. If your tool manipulates `PATH` around boxer, do not undo this:
a `uname` shim becomes `boxer run -- uname` inside a boxer already working on the same sandbox,
and the session deadlocks.

**A sandbox costs about 700 MB of disk.** It also holds around a gigabyte resident against a
default 4 GB allocation, so a tool that opens one per task should have an opinion about closing
them and about what it allocates. `boxer gc` and `auto_reclaim` are the built-in answers;
`boxer down --scope NAME` is the explicit one.

**Use `auto:` ports in anything you generate.** A fixed host port collides the moment a second
worktree starts, which is the ordinary case for anything that opens worktrees.
