This page covers the whole mechanism. [Scopes and packs](/docs/concepts/scopes-and-packs) goes
deeper on those two, and the [glossary](/docs/reference/glossary) defines every term.

## Scope: one VM per worktree

A **scope** is what boxer keys a sandbox to. By default it is the git worktree (a checkout made by
`git worktree add`, or the main checkout) that contains the current directory. Two worktrees of the
same repository get two VMs; two directories in one worktree share one.

Orchestrators such as Conductor, T3 Code and Paperclip cut a worktree per task, so each task gets
its own VM with no extra setup.

```toml
isolation = "worktree"   # default. also: session, subagent, repo
```

`session` and `subagent` key the VM to an agent session id instead, for harnesses that supply one;
without an id boxer falls back to the next wider scope. `repo` puts every worktree of the
repository on one VM.

## What the first command does

1. Resolve the scope from the working directory.
2. Read `boxer.toml` from the worktree, then the repository root, then `~/.config/boxer/`. The
   first one that sets a key wins.
3. Create the VM: image, CPUs, memory, and the worktree mounted at `mount_at` (`/workspace`).
4. Run `image_setup` if this image has not had it, then `setup` if this worktree has not.
5. Start anything in `start`, and wait for `ready`.
6. Run the command.

Steps 4 and 5 are skipped when their markers say they are done, which is why later commands are
fast. [The guest environment](/docs/guides/environment#dependencies) explains the difference
between `image_setup`, `setup` and `[prep]`, and which to use.

## Environment packs

On smolvm, after `image_setup` succeeds, boxer snapshots the VM into an **environment pack**. Later
VMs with the same environment start from the pack instead of repeating `image_setup`. The pack is
keyed on the image plus `image_setup`, `env`, `mounts`, `start` and `ready`; change any of them and
the next VM builds a new pack. Other backends have no packs and run `image_setup` in each new
sandbox.

`boxer up --rebuild` drops the pack and starts again, for when something outside those keys
changed, such as a moved base image tag.

## How a command reaches the guest

| Level | Mechanism | Enforces? |
| --- | --- | --- |
| MCP + skill | the agent chooses `boxer_run` | no |
| Hooks | boxer rewrites the command before it runs | yes |
| Plugin | same, in-process (OpenCode) | yes |
| PATH shims | a file named `npm` that re-runs itself in the guest | yes, where `PATH` holds |
| Inside | the harness runs in the VM | by construction |

`mode` sets how the hook behaves:

- `rewrite` (default): the agent types `npm test`, and boxer turns it into `boxer run -c 'npm test'`.
- `tool`: the shell is denied and `boxer_run` is the only way through, for harnesses that can block
  a command but not rewrite one.
- `off`: boxer stays installed and does nothing.

Hooks and shims act only on commands whose first word is on `intercept` (`npm`, `node`, `python`,
`go`, `make` and others by default). [Enforcement](/docs/guides/enforcement) covers each level.

## What runs on the host

`git`, `gh`, `ssh`, `boxer` and `smolvm` run on the host by default. They need your credentials and
the real repository. `passthrough` is that list; `intercept` is its opposite.
