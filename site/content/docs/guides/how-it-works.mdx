---
title: How boxer runs a command
description: What boxer does between an agent typing a command and the command running in the sandbox.
---

boxer finds the sandbox for your working directory, creates and prepares it if needed, and runs
the command in it with the worktree mounted at `/workspace`.

```sh
boxer run -c 'npm test'
```

## Scope

A **scope** is the key boxer gives a sandbox. By default it is the git worktree that contains the
current directory, so two worktrees of one repository get two sandboxes, and two directories in
one worktree share one.

```toml
isolation = "worktree"   # the default. Also: repo, session, subagent
```

`repo` puts every worktree of the repository on one sandbox. `session` and `subagent` key it to an
id the harness supplies, and fall back to the next wider scope when there is none.
[Scopes and packs](/docs/concepts/scopes-and-packs) has the rules.

## What the first command does

1. Resolve the scope from the working directory.
2. Read configuration. `boxer.toml` in the worktree wins over the one at the repository root, which
   wins over `~/.config/boxer/boxer.toml`, which wins over `.devcontainer/devcontainer.json`.
3. Create the sandbox on the configured backend (smolvm by default) with the image, `cpus`,
   `memory` and the worktree mounted at `mount_at`. Any `[prep]` commands start on the host at the
   same time.
4. Run `image_setup` if this sandbox has not run it, then `setup` if this worktree has not.
5. Launch `start` and poll `ready` until it passes.
6. Run the command.

Steps 3 to 5 happen only when the sandbox is missing or stopped, so later commands go straight to
step 6. [Set up the guest environment](/docs/guides/environment) covers each key.

On smolvm, boxer snapshots the sandbox after `image_setup` into an **environment pack**, and the
next worktree with the same image and `image_setup` starts from the pack instead of running it.
`boxer up --rebuild` drops the pack and prepares from scratch.
[Scopes and packs](/docs/concepts/scopes-and-packs#packs) lists what the pack key includes.

## How a command reaches the sandbox

The **integration level** is how an agent's command gets to boxer.
[Connect your harness](/docs/start/harnesses) shows which levels each harness supports.

| Level | Mechanism | Enforces |
| --- | --- | --- |
| MCP and skill | the agent chooses the `boxer_run` tool | no |
| Hooks | boxer rewrites the command before the harness runs it | yes |
| Plugin | the same, in-process (OpenCode) | yes |
| PATH shims | a file named `npm` that re-runs the command through boxer | yes, while `PATH` holds |
| Inside | the harness itself runs in the sandbox | yes |

The first four run the harness on the host, which boxer calls **outside**.
[Run the harness inside](/docs/guides/inside) covers the fifth.

`mode` sets what a hook does:

- `rewrite` (the default) turns `npm test` into `boxer run -c 'npm test'`.
- `tool` denies the shell command and points the agent at `boxer_run`, for harnesses that can
  block a command but not rewrite one.
- `off` leaves boxer installed and does nothing.

Hooks and shims act only on commands whose first word is on `intercept`, which defaults to `npm`,
`npx`, `pnpm`, `yarn`, `bun`, `node`, `python`, `pip`, `uv`, `pytest`, `cargo`, `go`, `make` and
a few more. [Enforcement](/docs/guides/enforcement) covers each level.

## What runs on the host

`git`, `gh`, `ssh`, `boxer` and `smolvm` stay on the host, because they need your credentials and
the real repository. That list is `passthrough`. A command on neither list runs on the host too,
which is why [tasks](/docs/guides/tasks) exist.
