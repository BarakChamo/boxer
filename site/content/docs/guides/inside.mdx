---
title: Run the harness inside
description: Run the agent itself in the VM, when to choose that, and what it costs.
---

Inside mode runs the harness itself in the guest. Every other
[integration level](/docs/guides/enforcement) leaves the harness on the host and intercepts what it
runs, so a command can slip past: one composed in an unusual way, one run through a login shell
that rebuilt `PATH`, or a program not on `intercept`. In inside mode no harness process runs on the
host.

```sh
boxer shell claude          # a terminal harness, in the VM
boxer acp gemini            # the harness's ACP server, stdio piped to an editor
```

Supported: `claude`, `codex`, `copilot`, `fx`, `gemini`, `grok`, `kimi`, `opencode`, `pi`. `fx` and
`pi` have no ACP server, so they are `shell` only. The matrix measured Claude Code, Codex, Kimi Code,
OpenCode and fx inside, 10 of 10 cells ([results](/docs/evals/results)).

## When to use it

- **You are defending against a hostile agent.** Outside mode leaves `git`, `gh` and `ssh` on the
  host by design, and any command boxer does not recognise runs there too. Inside mode has no host
  shell to reach.
- **The harness cannot be integrated from outside.** fx has no hooks, cannot be denied headlessly,
  and resolves commands past a PATH shim.
- **You want one mechanism for every harness.** No hook dialect, shim directory or rewrite rules.

## What it costs

The harness's credentials, configuration and model API all have to reach the guest.

**Configuration is mounted.** Every harness config directory on the host (`~/.claude`, `~/.codex`,
`~/.gemini`, and so on) is mounted read-write at the same path in the guest, and the harness's
config variable points at it. Sessions and file-based logins are shared with the host.

**Keychain logins are not.** A Linux guest has no macOS Keychain. boxer detects this and prints the
fix before the run:

```console
$ boxer shell claude
boxer: Claude Code's macOS Keychain login does not enter the VM; run `claude setup-token`
       on the host and export CLAUDE_CODE_OAUTH_TOKEN
```

Copilot's device login lands under `~/.copilot`, which is mounted, so it travels. fx keeps its
credential in the Keychain unless told otherwise, so boxer sets `FX_DISABLE_KEYCHAIN=1` and reads
`AI_GATEWAY_API_KEY` from the environment.

**The model API has to be reachable.** Inside mode adds each harness's API hosts
(`api.anthropic.com`, `api.openai.com`, `api.x.ai` and the rest) to the network allowlist, along
with the npm and Debian registries. An allowlist of your own must include them. On a backend
without the allowlist, set `network.mode = "on"` ([backends](/docs/concepts/backends)).

**The VM carries the harness as well as the work.** Give it more memory than an outside sandbox.
The default image is `mirror.gcr.io/library/node:24-bookworm-slim`, since most of these harnesses
are npm packages.

**The harness's own sandbox is turned off.** Codex's bwrap cannot start inside the guest, and Claude
Code declines to run as root. boxer sets what each needs (`IS_SANDBOX=1`,
`sandbox_mode="danger-full-access"`), and the VM is the sandbox.

## The first run installs the harness

The first run installs the harness in the guest. On smolvm boxer saves the result as a
[pack](/docs/concepts/scopes-and-packs), so later VMs start with it installed. Other backends
install it once per sandbox.

```console
$ boxer shell codex
boxer: installing codex in the sandbox (once per host)
```

If that install is interrupted, run `boxer up --recreate`.

## Paths

Inside mode mounts the worktree at its host path instead of `/workspace`, so file paths the harness
prints (references, diffs, errors) are valid on the host.

## Editors over ACP

`boxer acp <harness>` runs the harness's ACP server in the VM over stdio. Point the editor's agent
command at it:

```json
{ "command": "boxer", "args": ["acp", "gemini"] }
```

## Orchestrators that spawn a harness binary

```sh
boxer shim install --harness claude,codex
```

This writes a shim named after each harness binary that runs `boxer shell <harness>`. An
orchestrator that spawns `claude` from that directory runs the harness in the VM. Conductor,
Multica and T3 Code take a binary path; see [Orchestrators](/docs/guides/orchestrators).

## Inside or outside

| | Outside | Inside |
| --- | --- | --- |
| What runs on the host | the harness | `boxer` only |
| Can a command miss the sandbox | yes, for what `intercept` does not name | no |
| Credentials in the guest | none | the harness's |
| Memory | the work | the work and the harness |
| Harnesses | nine, at the levels in [this table](/docs/guides/enforcement) | nine, through one mechanism |

The two sets differ. DSH has no inside support, and fx has no outside support. Inside and outside
produce different [scopes](/docs/concepts/scopes-and-packs#placement-is-part-of-the-key) for the same
worktree, so each placement gets its own VM from the same `boxer.toml`.
