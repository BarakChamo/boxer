---
title: Forking a sandbox
description: Copy-on-write children of a running sandbox, what they are good for, and what they are not.
---

`boxer fork` branches the running sandbox into children that share its memory and disks
copy-on-write. A child does not boot: it starts from the parent's running state, dependencies
warm and services already up.

```sh
boxer fork --prepare --count 4
boxer run --scope swift-crab-f1 -c 'npm test -- --shard=1'
boxer fork rm --all
```

## Children share the worktree

This is the boundary of the feature, and it is imposed by smolvm rather than chosen: a branch
child inherits its parent's mounts and cannot override them, and smolvm refuses outright to
branch a machine whose mount is staged —

```
fork: staged mounts cannot be branched yet because multiple descendants would
synchronize into the same host directory
```

— so there is no private copy to hand a child. Every fork of a worktree sees the same files, and
two children writing one file race each other exactly as two processes on your machine would.

<Callout type="warn">
Forks are warm workers over one worktree, not isolated environments. Use them for work that
shards cleanly — test shards writing to separate paths, read-mostly checks, a warm start for
something that writes elsewhere. For work that edits the same files, use a second git worktree,
which gets its own sandbox and its own copy by construction.
</Callout>

## Preparing is explicit

A source must have been started as a branch source (`smolvm machine start --branchable`), which
is a property of the current boot. Preparing restarts the sandbox, so it ends whatever is running
in it, and boxer will not do that because you typed six letters:

```console
$ boxer fork
boxer: this sandbox was not started as a branch source, so it cannot be forked. Preparing
  restarts it, which ends whatever is running in it
  cause:     NOT_FORKABLE
  fix:       boxer fork --prepare
```

A stop ends branchability with the process that held it, so a sandbox that has been down needs
preparing again.

## Working with children

```sh
boxer fork ls                    # this scope's children
boxer run --scope <name> -c '…'  # run in one
boxer fork rm <name> | --all     # reclaim them
```

A child is named after its parent — `sb-7e1852e4a3c3-f1`, or `swift-crab-f1` — and either form
works wherever `--scope` is taken. A child has no worktree of its own, so it is addressed by name
rather than resolved from a directory.

`--count` is how many children the scope should have, so asking twice for four makes four, not
eight. `boxer ls` shows children beside sandboxes, and `boxer gc` reclaims a child whose parent is
gone. A fork costs what a sandbox costs.

## What forking is not

It is not a checkpoint. smolvm can write a real `.smolcheckpoint` — RAM, processes and all, as a
portable file — but it refuses on any machine holding a host mount, and boxer always mounts the
worktree. Resume-from-RAM is out of reach for a boxer sandbox by construction. What boxer can
carry between hosts and between days is the filesystem: see
[named packs](/docs/concepts/scopes-and-packs).
