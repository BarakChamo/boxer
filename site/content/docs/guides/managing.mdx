---
title: Manage sandboxes
description: List every sandbox on the machine, remove the ones you do not need, and check that backends and integrations work.
---

`boxer ls` lists every sandbox with its worktree, `boxer rm` and `boxer gc` remove them, and
`boxer backends` and `boxer integrations` check what boxer depends on.

## List sandboxes

```console
$ boxer ls -A
NAME          SCOPE            STATE    BACKEND  BRANCH            GIT       ATTACHED     SERVES                              WORKTREE
swift-crab    sb-7e1852e4a3c3  running  smolvm   fix-ui ↑2↓0 #42   dirty(3)  claude-code  https://fix-ui.myapp.localhost:1355  ~/src/myapp-fix-ui
olive-fern    sb-2b107321041f  running  docker   main              gone      codex        -                                   ~/src/old-task
→ boxer rm --gone  1 sandbox serves a worktree that no longer exists
```

- `-A` (`--all-backends`) looks on every installed backend, not only the configured one.
- `SCOPE` is the sandbox's key; see [scopes](/docs/concepts/scopes-and-packs).
- `BRANCH` is the worktree's branch and its distance from upstream. `--pr` adds its pull request
  through `gh` (a network call per worktree, so it is opt-in).
- `GIT` is `clean`, `dirty(n)`, or `gone`: the worktree was deleted and the sandbox is waiting to
  be reclaimed.
- `ATTACHED` is the harness and session that created it, if they reported one.
- `SERVES` is its [URL](/docs/guides/urls), or its forwarded port.
- `--resources` adds memory, CPU and disk.

`boxer status` is the same for this worktree alone; `boxer url` prints only its address.

## Remove sandboxes

```sh
boxer rm swift-crab             # by name or scope key
boxer rm --gone                 # every sandbox whose worktree no longer exists
boxer rm --stopped              # every one that is not running
boxer rm --all                  # every one on the configured backend (-A: every backend)
boxer rm -i                     # choose from a list
boxer stop swift-crab           # stop without removing
```

`rm` also removes everything boxer kept about the sandbox, including its run record, its lock and
its URL. A filter (`--gone`, `--stopped`, `--all`) asks before removing anything, and `-y` skips the
question. A sandbox named on the command line is removed without asking.

## Reclaim space

```sh
boxer gc --dry-run    # print what would go
boxer gc              # sandboxes whose worktree is gone or unused past idle_timeout, and old packs
boxer gc --all        # also every stopped sandbox and every unreferenced pack; running ones stay
```

`idle_timeout` defaults to `2h`. With `auto_reclaim` on (the default), ordinary commands run the
same sweep in the background at most every `reclaim_every` (`6h`).

## Check the backends

```console
$ boxer backends --probe
BACKEND    STATUS  VERSION  BOUNDARY   ALLOWLIST  SANDBOXES  PROBE
smolvm *   ready   1.16.1   kernel     yes        0          ok 7.0s
docker     ready   29.4.0   namespace  no         0          ok 0.3s
podman     ready   5.8.7    namespace  no         0          ok 0.5s
container  ready   1.4.1    kernel     no         0          ok 1.0s
```

This run is from an Apple Silicon Mac with every image cached; a first probe also pulls one.

`*` marks the configured backend. Without `--probe`, boxer only asks each runtime whether it
answers. With it, boxer creates a sandbox on each, runs a command, checks the write reached the
host, and removes it. Known misconfigurations are named under the table; see
[Backends](/docs/concepts/backends#known-runtime-problems).

## Check the integrations

```console
$ boxer integrations
INTEGRATION  KIND          ON PATH  THIS REPO  USER  SKILL
claude-code  harness       yes      yes        -     yes
codex        harness       yes      -          yes   yes
copilot      harness       yes      -          -     -
conductor    orchestrator  -        -          -     -
git-hook     orchestrator  -        yes        -     -
portless     tool          yes      -          -     -
→ boxer integrations add <name>  on PATH and not wired to boxer: copilot
```

The table shows, for each integration, whether its program is on `PATH`, whether boxer's hooks, skill and MCP
entry are installed in this repository and for your user, and whether the installed files came
from another boxer release (`stale`). The check asks `boxer install` which files it would write,
so the two agree.

```sh
boxer integrations add claude-code    # the same as boxer install claude-code
```

To install the skill or the plugin package, see [Skills and plugins](/docs/guides/skills-and-plugins).

## Choose the output format

These commands adapt to who is reading:

- a person at a terminal: colour, aligned tables, a `→` hint about what to run next, and a
  question before anything destructive;
- an agent or a pipe: plain text, a `next:` line with the exact command, and no prompts. A
  command that would have asked instead refuses and says what flag to pass;
- a program: `--json`.

| | |
| --- | --- |
| `--json` | one JSON document on stdout, on any command that has a JSON form |
| `BOXER_OUTPUT=json` | the same, for a caller that cannot add a flag |
| `BOXER_OUTPUT=text` / `human` | force plain or human output |
| `BOXER_AGENT=1` | mark an agent whose shell runs on a terminal |
| `NO_COLOR` | no colour, even for a person |

Claude Code is recognised by the `CLAUDECODE` variable it sets; other agents run commands without
a terminal, which is enough. The table layout is not a contract: parse `--json`. The shapes are in
the [JSON reference](/docs/reference/json).

```sh
boxer completion zsh > "${fpath[1]}/_boxer"    # or bash, fish
```
