## Choosing an image

```toml
image = "node:24-bookworm-slim"
```

Any OCI reference works. Without one, boxer picks an image from your lockfile: `package-lock.json`
gets node, `requirements.txt` gets python, and so on, falling back to `debian:bookworm-slim`.

**Prefer a small image.** A microVM starts by attaching the image's filesystem, so image size is
start-up time on every `boxer up`. Measured on an M4 with the pack already built:

| image | `boxer up` | first pack build |
| --- | ---: | ---: |
| `alpine:3.21` | 0.6s | 8.6s |
| `node:24-alpine` | 1.7s | 10.9s |
| `node:24-bookworm-slim` | 2.5s | 13.4s |
| `node:24-bookworm` | 9.5s | 26.2s |

The inferred images are all slim for this reason. Alpine is faster but uses musl rather than glibc,
so a dependency that ships only a glibc prebuilt breaks with an unclear error. Use it when you know
your dependencies.

A slim image has no compiler. If a dependency builds from source, install the toolchain in
`image_setup` rather than switching to the full image: on smolvm, `image_setup` is captured in the
pack, so you pay for it once per host rather than on every start.

A local image also works, for a repository that builds its own:

```toml
image = "./dev.tar"        # docker save archive
image = "./rootfs"         # extracted rootfs directory
image = "-"                # read from stdin
```

Nothing is pulled for these, so no registry host has to be allowed.

<Callout>
Use a registry mirror for public images. Docker Hub allows 100 anonymous pulls an hour, which a
machine running several sandboxes can reach. `mirror.gcr.io/library/node:24-bookworm-slim` has no
quota.
</Callout>

## Dependencies

Three keys install things. They differ in where they run and how often:

| key | runs | how often | use it for |
| --- | --- | --- | --- |
| `image_setup` | in the guest, before `setup` | once per VM; on smolvm the result is captured in an [environment pack](/docs/concepts/scopes-and-packs), so later VMs skip it | system packages, global tools, compilers |
| `setup` | in the guest, in the mounted worktree | once per worktree, and again when the list changes | `npm ci`, `uv sync`: anything that writes into the worktree |
| `[prep] commands` | on the host, while the sandbox boots | once per worktree | fetching dependencies with prebuilt binaries, opt-in |

```toml
image_setup = ["npm i -g typescript"]   # once per image on smolvm, captured in the pack
setup = ["npm ci"]                       # once per worktree, lands in your files
```

Do not put `npm install` in `image_setup`. The pack records it as done, but `node_modules` is in
the worktree, which the pack does not carry, so the next worktree has no dependencies.

Installing through the guest's mount is the slow part of a first start. Two features reduce it.

**Host package caches are mounted read-only by default**, detected from the lockfile: `~/.npm` for
`package-lock.json`, the uv and cargo caches for theirs. The install still runs in the guest, so
native binaries are still chosen for the guest's platform; only the download is saved.

```toml
[cache]
enabled  = true          # the default
managers = ["auto"]      # or an explicit list: npm, pnpm, yarn, bun, uv, poetry, cargo, go
```

**`[prep]` runs on the host before the sandbox exists**, in parallel with its boot, and finishes
before `setup` starts. It is the equivalent of devcontainer's `initializeCommand`. It is opt-in
because it is correct only for packages that ship prebuilt platform binaries.
`$BOXER_TARGET_FLAGS` carries the guest's platform so npm and bun fetch the right ones:

```toml
[prep]
commands = ["npm ci $BOXER_TARGET_FLAGS"]   # --os=linux --cpu=arm64 --libc=musl on an alpine image
```

A package that compiles at install time (`better-sqlite3`, `node-pty`) builds for the host whatever
the flags say, and fails in the guest with `invalid ELF header`. `boxer doctor` names any such
package in your lockfile; install those in `setup`.

### From a devcontainer

If the repository has `.devcontainer/devcontainer.json`, boxer reads the image, lifecycle commands,
ports, environment, mounts and user from it, and resolves its `${localWorkspaceFolder}`-style
variables. It reports anything it will not do, such as `features` or `runArgs`. `boxer.toml`
overrides it. The mapping is in the [configuration reference](/docs/reference/configuration#devcontainerjson).

You will usually still need a short `boxer.toml` for the **allowlist**. boxer's default network
reaches the image registry and nothing else, so a `postCreateCommand` that installs packages needs
the package registry in `network.allow_hosts`. When it is missing, the failed install names the
refused host.

## Services

`start` launches long-running processes; `ready` is a command boxer polls until it succeeds.

```toml
start = ["npm run dev"]
ready = "curl -sf http://127.0.0.1:3000/ >/dev/null"
ready_timeout = "120s"     # the default is 60s
```

`start` runs once per running VM, after `setup`, so it can depend on what `setup` installed. A
stopped VM has no processes, so the next start runs `start` again.

When `ready` never passes, the services' output is in `/tmp/boxer-start.log` in the guest, and
boxer quotes its tail in the error.

## Ports

```toml
[network]
ports = ["auto:3000"]
```

`auto:` takes a free host port and forwards it to 3000 in the guest. Use it in any `boxer.toml` you
commit: a fixed host port collides as soon as a second worktree starts.

<Callout type="warn">
**The server must bind `0.0.0.0` in the guest, not `127.0.0.1`.** A forward arrives on the guest's
network interface, so a server listening only on loopback never sees it. A `ready` probe inside the
guest can still pass against `127.0.0.1`, so it will not catch this.
</Callout>

```toml
start = ["npm run dev -- -H 0.0.0.0"]     # next
start = ["vite --host 0.0.0.0"]           # vite
```

`boxer status` prints where each guest port landed:

```console
$ boxer status
boxer: swift-crab (sb-7e1852e4a3c3) running, image node:24-bookworm-slim, mounted /Users/me/src/myapp -> /workspace
  port:      guest 3000 -> http://127.0.0.1:61234
```

<Callout type="warn">
A dev server reached through a forwarded port sees an unexpected origin. Next.js then refuses its
own dev chunks; add `allowedDevOrigins: ['127.0.0.1', 'localhost', '*.localhost']` to
`next.config.ts` (`*.localhost` covers [`[urls]`](/docs/guides/urls) names). Other frameworks have
an equivalent setting.
</Callout>

To give each worktree's server a stable name instead of a port, use [`[urls]`](/docs/guides/urls);
agents find it with `boxer url`.

## Environment variables and secrets

```toml
[env]
NODE_ENV = "development"          # configuration; travels into the pack

env_passthrough = ["CI"]          # read from the host at run time
secrets = ["NPM_TOKEN"]           # same, and never written anywhere
```

`env` is captured in the pack. Anything that should not be in a snapshot belongs in
`env_passthrough` or `secrets`, which are read from the host on each run. `env_passthrough`
defaults to `["CI"]`.

## Networking

```toml
[network]
mode = "allowlist"
allow_hosts = ["registry.npmjs.org"]
```

`on` allows everything, `off` allows nothing, and `allowlist` (the default) allows the image
registry plus the hosts you name. Only smolvm enforces the allowlist; see
[Backends](/docs/concepts/backends).
