## Choosing an image

```toml
image = "node:24-bookworm-slim"
```

Any OCI reference works. Leave it out and boxer infers one from your lockfile — `package-lock.json`
gets node, `requirements.txt` gets python, and so on.

**Pick a small image, and prefer it over a fat one you will not use.** A microVM starts by
attaching the image's filesystem, so the image's size is start-up latency you pay on every
`boxer up`. Measured on an M4 with the pack already built:

| image | `boxer up` | first pack build |
| --- | ---: | ---: |
| `alpine:3.21` | 0.6s | 8.6s |
| `node:24-alpine` | 1.7s | 10.9s |
| `node:24-bookworm-slim` | 2.5s | 13.4s |
| `node:24-bookworm` | 9.5s | 26.2s |

That is a 4x spread on start-up for the same runtime. The inferred defaults are all slim for this
reason. Alpine is faster still but links musl rather than glibc, so a dependency shipping only a
glibc prebuilt will break in a way that is hard to read — worth it when you know your
dependencies, not as a default.

A slim image has no compiler. If a dependency builds from source, add it to `image_setup` rather
than reaching for the fat image: `image_setup` is snapshotted into the pack, so you pay it once
per host instead of on every start.

It also takes a local image, which is the path for a repository that builds its own:

```toml
image = "./dev.tar"        # docker save archive
image = "./rootfs"         # extracted rootfs directory
image = "-"                # read from stdin
```

Nothing is pulled for these, so no registry host has to be opened.

<Callout>
Prefer a registry mirror for public images. Docker Hub's anonymous pull quota is 100 an hour, and
a machine running several sandboxes reaches it. `mirror.gcr.io/library/node:24-bookworm-slim` has
no quota.
</Callout>

## Dependencies

```toml
image_setup = ["npm i -g typescript"]   # once per image, captured in the pack
setup = ["npm ci"]                       # once per worktree, lands in your files
```

## Services

`start` launches long-running processes; `ready` is how boxer knows they are up.

```toml
start = ["npm run dev"]
ready = "curl -sf http://127.0.0.1:3000/ >/dev/null"
ready_timeout = "120s"     # the default is 60s
```

`start` runs once per running VM, after `setup`. A `boxer down` and a later start run them again —
the marker lives in the guest's memory-backed `/tmp` precisely so that a stopped VM has no
processes and knows it.

Running after `setup` is the whole point, and it is why boxer does not use smolvm's own
persistent workload (`machine create --init`) for this: that launches when the machine starts,
which is before `setup` has installed anything, so the ordinary `start = ["npm run dev"]` against
a worktree that `setup` populates would die immediately and never be relaunched.

When `ready` never passes, the services' own output is in `/tmp/boxer-start.log` in the guest, and
boxer quotes the tail of it in the error rather than making you go and look.

## Ports

```toml
[network]
ports = ["auto:3000"]
```

`auto:` asks the host for a free port and forwards it to 3000 in the guest. Use it in any
`boxer.toml` you commit: a fixed host port collides the moment a second worktree starts, which is
exactly what happens when an orchestrator opens three tasks at once.

<Callout type="warn">
**The server has to bind `0.0.0.0` in the guest, not `127.0.0.1`.** A forward arrives on the
guest's interface, and a process listening only on loopback never sees it. The symptom is a
forward that exists, a server that is running, and a browser that gets nothing.

```toml
start = ["npm run dev -- -H 0.0.0.0"]     # next
start = ["vite --host 0.0.0.0"]           # vite
```

A `ready` probe run inside the guest may still pass against `127.0.0.1`, so it is not the check
that catches this.
</Callout>

`boxer status` prints what the guest port actually landed on:

```console
$ boxer status
sb-7f2a91 running · node:24-bookworm-slim · 3000 → 61234
```

<Callout type="warn">
A dev server reached through a forwarded port sees a different origin than it expects. Next.js
refuses its own dev chunks in that case; add `allowedDevOrigins: ['127.0.0.1', 'localhost']` to
`next.config.ts`. Other frameworks have the same knob under different names.
</Callout>

## Environment variables and secrets

```toml
[env]
NODE_ENV = "development"          # configuration; travels into the pack

env_passthrough = ["CI"]          # read from the host at run time
secrets = ["NPM_TOKEN"]           # same, and never written anywhere
```

`env` is configuration and is captured in the snapshot. Anything you would not want in a snapshot
belongs in `env_passthrough` or `secrets`, which are read from the host on each run.

## Networking

```toml
[network]
mode = "allowlist"
allow_hosts = ["registry.npmjs.org"]
```

`on` allows everything, `off` allows nothing, `allowlist` allows what you name. The allowlist is
the useful default for a build: dependencies resolve, and a command that decides to phone somewhere
else does not.
