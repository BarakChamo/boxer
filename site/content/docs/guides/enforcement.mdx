---
title: Enforcement and its limits
description: Which integration mechanisms enforce the sandbox, which only ask, and where each breaks.
---

An integration level is how boxer gets an agent's commands into the sandbox. They are not equally
strong: hooks, the OpenCode plugin and inside mode enforce; PATH shims enforce only where `PATH`
is not rebuilt; the skill only asks. `intercept` in `boxer.toml` is the list of programs routed to
the sandbox (see [configuration](/docs/reference/configuration)).

## Hooks

Where a harness has a hook API that accepts a rewritten command, boxer uses it. The agent runs
`npm test`; boxer sees the call before it runs, matches `npm` against `intercept`, and replaces the
command with `boxer run -c 'npm test'`. The agent sees no refusal.

This holds regardless of shell, `PATH` or how the command was composed, because interception
happens before the shell. Claude Code, Codex, Grok, Gemini CLI and Copilot accept a rewrite.

## Tool mode

For harnesses that can block a command but not rewrite one. `mode = "tool"` denies the shell and
leaves the `boxer_run` MCP tool as the way through. An agent that uses the tool is never denied; one
that reaches for the shell gets a refusal saying to use the tool.

## The OpenCode plugin and pi extension

OpenCode and pi have TypeScript plugin APIs instead of hooks. boxer's plugin (OpenCode) and
extension (pi) see the shell call and replace the command before it runs, so they enforce as a hook
does. `boxer install opencode` and `boxer install pi` write them; pi loads project extensions only
once the project is trusted (for a one-off run, `pi -e .pi/extensions/boxer.ts`).

The rewrite happens in-process and writes no rewrite line to the trace, so the evaluation matrix
reads OpenCode's evidence differently.

## PATH shims

```sh
boxer shim install ~/.boxer/shims
```

Needs no harness cooperation. This writes one file per entry in `intercept`, each of which re-runs
itself in the guest. Put the directory first on the harness's `PATH` and a bare `npm` goes to the
sandbox. Two things break it:

<Callout type="warn">
**Never shim the runtime your harness is written in.** A `node` shim shadows a node-based
harness's own interpreter, and the harness dies at startup. For shims, `intercept` should name
build tools, not interpreters.
</Callout>

<Callout type="warn">
**A login shell rebuilds `PATH`.** On macOS `/etc/zprofile` runs `path_helper`, which puts system
directories first, so a harness that runs `zsh -lc` or `bash -lc` (Codex does) gets `/usr/bin/npm`.
`boxer doctor` detects this. Use hooks or tool mode for those harnesses.
</Callout>

## Shimming the shell instead

There are two forms.

**A `bash` entry on `intercept`** writes a `bash` shim like any other, so a harness that resolves
`bash` on `PATH` runs every command in the sandbox. One file, and nothing that can shadow an
interpreter. A harness that spawns `/bin/bash` by absolute path bypasses it.

```toml
intercept = ["bash"]
```

**`boxer shim install --shell`** writes `boxer-bash`, a bash whose every command runs in the
guest. It is not found through `PATH`: point the harness's shell setting at it (`shell_path` in
OpenHands, `terminal.default_shell` in herdr). This level, shell substitution, needs a harness
whose shell is configurable; see [results](/docs/evals/results).

```sh
boxer shim install --shell ~/.boxer/shims
```

Which fits depends on the harness; the [evaluation matrix](/docs/evals/matrix) measures both.

## Inside mode

```toml
integration = "inside"
```

The harness itself runs in the VM, so there is nothing on the host to intercept. `boxer shell
claude` starts it. The harness's credentials and config have to reach the guest, and the VM needs
more memory. See [Running the harness inside](/docs/guides/inside).

## The skill

Every level ships a skill telling the agent that commands go through boxer. On its own it does
not enforce anything: an agent that ignores it is not sandboxed. It is the fallback for a harness
with no integration, and the `adherence` evaluation tier measures how often agents follow it.

## Harnesses that sandbox themselves

Codex has its own seatbelt/landlock sandbox, and a hypervisor cannot start inside one. Run Codex
with `--sandbox danger-full-access` (or `--dangerously-bypass-approvals-and-sandbox` under
`codex exec`) when boxer is the sandbox.

The same applies to any harness that confines its own process: the host-side `boxer` process needs
the hypervisor (Hypervisor.framework on macOS, `/dev/kvm` on Linux) to start a VM. Inside mode turns each harness's own sandbox off in the
guest for you.

`BOXER_INSIDE=1` is set in every guest process boxer starts, so a boxer inside a guest does not
wrap commands a second time.

## Checking what holds

```sh
boxer doctor
```

It prints the integrations it finds, the enforcement in effect, and setups that look right but
will not hold.
