description: Install boxer into your coding agent once. Every worktree it works in gets its own sandbox, automatically.

boxer gives every git worktree its own sandbox and runs your coding agent's commands in it. You
install it into your agent once. After that you work as usual, and boxer handles the sandboxes.

![Three coding agents in three git worktrees, each running in its own boxer microVM with its own dev server URL](/hero.svg)

## Why

Codex and Claude Code create worktrees themselves, and orchestrators like Conductor run a task per
worktree. Each worktree has its own files, but every task still shares your machine. Two dev
servers fight over port 3000, one task's install breaks another's, and every command runs against
your own system. boxer gives each worktree its own sandbox:

- **A sandbox per worktree**, created when an agent starts working there, including worktrees the
  agent or an orchestrator creates.
- **No change to your agent.** A hook rewrites `npm test` into the sandbox before the shell runs it.
- **No port clashes.** Every worktree serves port 3000 inside its sandbox, and gets its own
  `https://<branch>.<repo>.localhost` outside.
- **A real boundary.** Each sandbox is a microVM with its own kernel. It sees only the worktree.
- **33 ms per command**, within 4 ms of `docker exec`. See [Benchmarks](/docs/evals/benchmarks).
- **Local.** No account, no upload. See how it [compares](/docs/comparison) with the alternatives.

## What happens while your agent works

Once boxer is installed into your agent, this happens on its own:

1. **A session starts in a worktree.** boxer's `SessionStart` hook creates that worktree's sandbox. It
   boots the image, runs your `setup` (such as `npm ci`) and starts your dev server. Then it tells
   the agent that commands run in a sandbox, which ones stay on the host, and where its dev server
   is.
2. **The agent runs a command.** It types `npm test` as usual. boxer's `PreToolUse` hook rewrites it to
   `boxer run -c 'npm test'` before the shell runs it. The command runs in the sandbox, and the
   agent gets the normal output and exit code.
3. **A new worktree appears.** It does not matter who creates it: `codex --worktree`, Claude Code's
   `EnterWorktree`, `git worktree add` from the agent's shell, or an orchestrator. boxer picks the sandbox from the directory each command runs in. The first command in the new
   worktree creates its sandbox, with the same `setup` and `start`. Two worktrees never share a
   sandbox.
4. **A worktree is deleted.** boxer removes its sandbox. Any boxer command starts this cleanup in the background, at most every 6 hours (`auto_reclaim`). `boxer gc` runs it now.

`git`, `gh` and `ssh` always run on your machine, with your credentials. Everything in the
`intercept` list (`npm`, `node`, `python`, `go`, `make`, `cargo` and more) runs in the sandbox.

## What `boxer install` sets up

`boxer install <harness>` writes the files your agent reads. For Claude Code:

| Piece | What it does | Enforces |
| --- | --- | --- |
| Hooks, in `.claude/settings.json` | create the sandbox at session start, and rewrite each shell command into it | yes |
| MCP server, in `.mcp.json` | gives the agent a `boxer_run` tool and a live description of its sandbox | in tool mode |
| Skill, in `.claude/skills/boxer/` | explains to the agent how commands run here and what to do if one is refused | no |
| Subagent, in `.claude/agents/boxed.md` | a subagent that runs everything through boxer | no |

The hooks do the work. The other pieces help the agent understand the sandbox, so it does not
fight it. Commit the files. A worktree is cut from a branch, and the hooks have to be on it.

## How boxer connects to each agent

Agents expose different extension points. boxer uses the best one each agent has. Best means the
agent keeps working unchanged and a command cannot slip past to your machine. From best to
weakest:

| Level | How it works | Used for |
| --- | --- | --- |
| Hook rewrite | a hook changes the command before the shell runs it | Claude Code, Codex, Gemini CLI, Copilot CLI, Grok |
| Plugin or extension | the same, from inside the agent's process | OpenCode, pi |
| Tool mode | the hook blocks the shell, so the agent runs commands with `boxer_run` | Kimi Code, DSH |
| Inside mode | the agent itself runs in the sandbox, so nothing runs on your machine | fx, any agent without hooks, or when you want the agent off your machine too |
| PATH shims | files named `npm`, `node` and so on that forward to the sandbox | an extra layer, or agents without hooks |
| Skill and MCP tool only | the agent is asked to use boxer, and nothing forces it | agents boxer has no integration for |

`boxer install` sets up the level for your agent. Kimi Code and DSH also need one line in
`boxer.toml` to turn on tool mode. Inside mode is the strictest, but the agent's login and config
have to reach the sandbox, so it is opt-in. [Integration levels](/docs/setup/integration-levels) has
the details, and where each level can be bypassed.

podman also work, with less isolation. See [Backends](/docs/backends). boxer runs on macOS on Apple
Silicon, and Linux on x86-64 or arm64.
