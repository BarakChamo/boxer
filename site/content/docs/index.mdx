title: Introduction
description: boxer runs a coding agent's shell commands in a sandbox, one per git worktree.
---

boxer runs a coding agent's shell commands in a sandbox instead of on your machine. Each git
worktree gets its own sandbox, created on the first command, with the worktree mounted at
`/workspace`. The agent keeps working as before: it runs `npm test`, the command runs in the
sandbox from the matching directory, and the exit code, stdout and stderr come back unchanged.

```console
$ boxer run -c 'uname -a'
Linux sb-7f2a91 6.12.95 #1 SMP aarch64 Linux
```

The host here is a Mac. The default sandbox is a [smolvm](https://smolmachines.com) microVM with its
own kernel. Apple `container`, docker and podman are the [other backends](/docs/concepts/backends).

## What's included

boxer is one Go binary. The rest of this table is the ways to connect it to an agent or a program.

| Part | What it is | Docs |
| --- | --- | --- |
| `boxer` CLI | runs commands in the sandbox and manages sandboxes (`run`, `up`, `ls`, `rm`, `gc`, `doctor`) | [CLI](/docs/reference/cli) |
| Hooks | `boxer hook <harness>` rewrites or denies a harness's shell calls before they run | [Enforcement](/docs/guides/enforcement) |
| PATH shims | files named `npm`, `node`, `make` and so on that re-run themselves in the sandbox | [Enforcement](/docs/guides/enforcement#path-shims) |
| MCP server | `boxer mcp`: the `boxer_run` and `boxer_status` tools and the `boxer://brief` resource | [MCP](/docs/reference/mcp) |
| Skill | `skills/boxer`, in the Agent Skills format: how commands run here and what to do when refused | [Skills and plugins](/docs/guides/skills-and-plugins) |
| Plugin package | `plugin/`, in the Agent Plugins format: the skill, the MCP server, and each client's hooks | [Skills and plugins](/docs/guides/skills-and-plugins#the-plugin-package) |
| Inside mode | `boxer shell <harness>` and `boxer acp <harness>` run the agent itself in the sandbox | [Inside mode](/docs/guides/inside) |
| Go package | `pkg/boxer`: open, run and remove sandboxes from a Go program | [Building on boxer](/docs/guides/building-on-boxer) |
| JSON output | `--json` on every command that reports state, with stable fields and exit codes | [JSON](/docs/reference/json) |
| Evaluation suite | the smoke suite and `boxer-eval`, which run real harnesses against real sandboxes | [Evaluations](/docs/evals) |

## Pick a setup

| You run | Do this | You get |
| --- | --- | --- |
| Claude Code, Codex, Gemini CLI or Grok in a terminal | `boxer install <harness>` and commit the files | hooks that rewrite every intercepted command |
| Copilot CLI | `boxer install copilot --user` | the same hooks, in `~/.copilot` |
| OpenCode or pi | `boxer install opencode` or `boxer install pi` | a plugin or extension that does the same |
| Kimi Code or DSH | `boxer install <harness>`, then `mode = "tool"` | shell calls denied, `boxer_run` as the way in |
| An orchestrator (T3 Code, Paperclip, herdr, Conductor, Multica, OpenHands) | install for the harness it drives, then warm each worktree | the above, per task worktree |
| An agent you do not trust with a host shell, or fx | `boxer shell <harness>` | the agent itself in the sandbox |
| Your own program | `pkg/boxer` or `--json` | sandboxes under your control |

[Connect your harness](/docs/start/harnesses) and [Orchestrators](/docs/guides/orchestrators)
have the steps for each.

## What it is not

boxer protects your machine from what an agent runs. It does not protect the worktree: the agent is
there to change it, so the mount is read-write.

It is not a container runtime or a dev environment. The machines, images and snapshots belong to
the backend, and boxer keeps only small records that it removes with the sandbox.

It is not a defence against an attacker who knows they are in it. The threat model is a careless or
destructive agent. The [security model](/docs/concepts/security) says where that line is.
