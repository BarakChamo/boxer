---
title: What boxer is
description: One microVM per git worktree, so a coding agent's shell commands stop running on your machine.
---

Coding agents run shell commands. `npm install`, `make`, `python script.py`, whatever the model
decided would help. Those commands run as you, on your machine, with your credentials and your
filesystem.

boxer puts them in a [smolvm](https://smolmachines.com) microVM instead — one VM per git worktree,
started on the first command, with the worktree mounted in the guest at `/workspace`.

The agent is not told. It types `npm test`, the command runs in the VM, and the output comes back
looking exactly as it would have — same exit code, same stdout, same stderr, the working directory
mapped to the matching place under the mount.

```console
$ boxer run -c 'uname -a'
Linux sb-7f2a91 6.12.95 #1 SMP aarch64 Linux
```

That ran on Linux. The host is a Mac.

## What it is not

The worktree is mounted read-write, because the agent is there to change it. boxer keeps commands
away from everything else on your machine, not away from the code you asked the agent to work on.

boxer is not a container runtime, and it does not replace your dev environment. It is a shim
between a coding agent and the commands it wants to run, with a VM behind it. The VMs, their
images and their snapshots all belong to smolvm; boxer keeps no state of its own beyond a few
markers.

It is also not a security boundary against an adversary who knows they are in it. A microVM is a
real isolation boundary and a good one, but boxer's threat model is *an agent doing something
destructive or careless*, not *an attacker deliberately breaking out*. The
[security model](/docs/concepts/security) says exactly where that line falls, and what to do if
your threat model is the other one.
